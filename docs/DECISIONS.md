# 架構決策記錄（ADR）

> 本檔記錄已定案的決策、理由與後果。**未經討論不要推翻**；要改就新增一則 ADR 並標明取代關係。

---

## ADR-001：目標是「完整 MMO」，不是單機重製

**日期**：2026-10-16 ｜ **狀態**：已定案（使用者決定）

**決策**：本專案的交付物包含可運作的 **server（login / world / channel / game）與持久化**，
client 必須能與該 server 完整互動。

**後果**：
- 協定 = 一等公民：必須有單一來源（schema）與可測試的 codec，並被 client / server 共用。
- **必須先建立 oracle**：可以由「原 client ↔ 我們自寫的 server」驗證，或「重寫 client ↔ 原協定 server」；
  2003 首版沒有公開 server，因此**唯一可靠來源是原 client binary 本身**（見 ADR-004）。
- 里程碑的第一順位是「**能收下原 client 的封包並正確解析**」，而不是「畫面好看」。

## ADR-002：協定 schema-first + TypeScript 核心/server + Godot 4.x（GDScript）client

**日期**：2026-10-16 ｜ **狀態**：已定案（使用者對技術棧表示「都行」，由本評估擇定）

**決策**：
1. **協定以 schema 為單一來源**（`protocol/`）：由 schema 產生（或驗證）各語言的 codec。
2. **核心與 server 用 TypeScript**（Node 22，零依賴：原生 type stripping + `node --test`）。
3. **client 用 Godot 4.x + GDScript**（殼層：渲染 / 輸入 / UI / 音訊）。

**理由**：
| 考量 | 說明 |
|---|---|
| 完整 MMO 的關鍵是 **server + 協定** | 這兩者用同一套 TS 定義，單一語言即可覆蓋 80% 的邏輯面 |
| **跨平台（使用者第 3 點）** | Godot 4.x 可輸出 Windows / macOS / Linux / Android / iOS / **Web**；但 **C# 專案目前無法輸出 Web**（官方文件：C# 專案仍不能 export 到 web，GDScript 可以）→ 若要保留瀏覽器版本，client 必須是 GDScript |
| 可測試性 | TS 核心可在**不需要引擎**的情況下完整單元測試（本倉庫已可在沙箱內執行） |
| 避免語言鎖死 | 因為協定由 schema 產生，**未來若放棄 Web 想改用 C# client，只要換 binding，不動核心** |
| 簡單性 | 零依賴工具鏈（`node --test`、`python3 -m unittest`），無 build step、無框架 |

**被否決的選項與原因**：
- **C# 核心 + Godot C# client**：語言單一、型別最強，但 (a) C# 無法 export web，(b) 本沙箱無 .NET 可驗證，
  (c) 手機版 C# 仍屬實驗性。→ 若日後明確放棄瀏覽器且團隊偏好 C#，可以只換 client binding（見上「避免語言鎖死」）。
- **純 Unity**：授權與長期風險，且 2D MMORPG 用不到其優勢。
- **純 GDScript（引擎內含全部邏輯）**：server 無法共用邏輯，協定會複製兩份。

**後果**：
- 必須維護 schema → 產生/驗證 codec 的工具鏈（Phase 1 起）。
- client 端的「重邏輯」僅限於預測/插值/動畫；**數值與規則以 server 為準**。

## ADR-003：跨平台優先序

**日期**：2026-10-16 ｜ **狀態**：已定案（使用者：最好可以跨平台）

**決策**：優先序為 **Windows / macOS / Linux 桌面 → Web（瀏覽器）→ Android / iOS**。
以 Godot 4.x 匯出；不使用任何桌面平台專屬 API（Win32/COM/DirectX 一律不得出現在新程式碼中）。

**後果**：
- 不可使用 C#（因 Web 優先序高於「語言統一」）。
- 輸入層必須支援鍵盤 + 手把（日後觸控）；不可假設韓文 IME 永遠存在（原 client 依賴 IMM32）。
- 音訊/影像格式使用引擎原生格式（PNG/OGG），**不重寫 ijl15 / l3codeca.acm / DirectSound**。

## ADR-004：以「原 client 作為 oracle」，先做封包擷取

**日期**：2026-10-16 ｜ **狀態**：已定案

**決策**：在實作 gameplay 之前，先建立能**擷取並解析原 client 封包**的能力：
`server/` 提供 `capture` 模式（TCP listener，寫出 JSONL trace），並由 `docs/protocol/FINDINGS.md`
累積「已由 binary 證實」的協定事實。

**理由**：2003 KMS 1.11 沒有任何公開 server 或文件；所有協定知識只能來自：
1. 反編譯碼（dispatch / 讀寫欄位順序）→ 2. 實機擷取（原 client 指向我們的 listener）→ 3. 交叉驗證。

**後果**：
- 第一個「可對外展示」的成果不是遊戲畫面，而是**原 client 的握手封包被正確解析**。
- 任何未被上述兩者證實的協定欄位，一律標記 `HYPOTHESIS`，不得寫成既定規格。

## ADR-005：WZ／資產管線只實作一次，用 TypeScript（`server/src/wz/`）

**日期**：2026-10-16 ｜ **狀態**：已定案

**決策**：`Data.wz` 的讀取與資產輸出（目錄樹、值層、像素、PNG）以 **TypeScript 實作於
`server/src/wz/`**，作為產品端唯一一份；Python 的 `tools/wz1.py`／`wzimg.py`／`wzdata.py`
**降級為反編譯與驗證用的參考實作**（兩邊的黃金值必須一致，見 `server/test/wzimg.test.ts`
與 `tools/tests/test_wzimg.py`），不再新增 Python 端資產工具，原路線圖的
`tools/wz2assets.py` 取消。

**理由**：
1. 遊戲程式是 TypeScript（ADR-002）：伺服器要地圖／怪物資料，Godot 客戶端要 PNG／動畫。
   若資產管線另寫一份 Python，同一份 WZ 語意就會有**兩份會各自漂移的實作**。
2. 反編譯 dump 是 CP949 的 C，Python 在「快速試錯、和 binary 對照」上更順手，所以探索階段
   留在 `tools/`；一旦語意確定（`docs/WZ1_FORMAT.md` §4 全部 ✅）就只留一份產品實作。
3. 兩份實作對同一組黃金值（1,052 張 image、922 declared + 130 scanned、55,379 張 canvas、
   696,774 次名稱表查詢、第一張 canvas 像素的 sha256）互相驗證，比任何註解都可靠。

**後果**：
- 資產輸出（PNG）由 `server/src/wz/png.ts` 產生，指令是 `node server/src/cli.ts wz png`。
- `tools/` 只做「讀 .c／驗 WZ 語意」；新增 WZ 功能一律加到 `server/src/wz/`。
- 兩邊不一致時以 `docs/WZ1_FORMAT.md` 的證據為準，並同時修正兩份實作與測試。

## ADR-006：怪物傷害先「照 client 說的記帳」，把驗證留給之後的同一條迴圈

**日期**：2026-10-16 ｜ **狀態**：已定案（可再評估）

**決策**：伺服器對 `0x0F`／`0x10`／`0x11` 帶進來的傷害值**先照單全收**：扣怪物的 HP、
回應 `0x34`／死亡時 `0x30`／收屍與重生用 `0x31`（FINDINGS §4.17）。
**不重算傷害**，也**不先做客端驗證**，但把「重算」的兩個前提寫下來，讓它之後可以補上。

**理由**：
1. **這是 2003 client 的實際分工**：傷害由攻擊方的 client 算完、畫完才寫進封包
   （`sub_512F90` 呼叫 `sub_4882F0` 把 `CMob::DAMAGEINFO` 排進怪物自己身上，見 §4.13.1／§4.17），
   伺服器在原始設計裡就是記帳的一方。我們的目標是「先讓原 client 能玩完一個迴圈」。
2. **重算需要兩塊我們還沒有的東西**：client 的傷害公式（散在 `sub_512F90` 一族與技能表裡，尚未 RE）
   與「哪一顆亂數」（`0x16` 的三個 `u32` 是 client 自訂 RNG 的種子，`src/protocol/random.ts`
   已是逐位元移植）。有了這兩塊，重算就是同一個 RNG 的第二次抽樣，而不需要新機制。
3. **現在就驗證會把還沒解出的知識硬編碼成規則**，違反 `GODOT_MIGRATION_PROMPT.md` 的證據優先順序。

**後果**：
- 目前任何人都能送假的傷害值 —— 這是**已知且刻意**的缺口，不是疏漏；在 Phase 2 的
  「共享世界」之前，`MobField` 還是每個連線一份，這個缺口不會外溢到別的玩家。
- 之後要補驗證時，落點是同一個函式（`GameEntryServer.applyAttack` → `MobField.applyDamage`）：
  在那裡用 `ClientRandom` 重抽一次並比對，就變成「一次改動、一個測試」。
- 怪物 HP 是伺服器的權威資料：即使傷害值不檢查，**誰能被打、還剩多少 HP、什麼時候重生**
  都由伺服器決定（client 報的 `mobId` 必須存在於自己的場地，否則只寫 log）。

## ADR-007：掉落與金錢的「伺服器自訂參數」先集中成常數，並記下它們不是證據

**日期**：2026-10-16 ｜ **狀態**：已定案（可再評估）

**決策**：掉落與拾取的行為（`0x43`／`0x44`／`0x0B`／`0x11` 的收送時機，FINDINGS §4.18）已實作成
`server/src/game/drops.ts` 與 `server/src/game/rewards.ts`，其中**binary 沒有、由本專案選擇**的數字
全部集中在這兩個檔案的常數，並在註解裡明說「這是伺服器的選擇」：

| 常數 | 值 | 為什麼是選擇 |
|---|---|---|
| `MESO_DROP_CHANCE_PER_MILLE` / `MOB_JUNK_CHANCE_PER_MILLE` / `MOB_POTION_CHANCE_PER_MILLE` | 600 / 300 / 50 | 原伺服器的掉寶率在 client 裡不存在（掉落是 `0x43` 單向宣告）|
| `MESO_PER_LEVEL` | 3 | 金額公式 `1 + range(0, level * 3)` 的上界 |
| `POTION_BY_LEVEL` | 4 個等級帶 | 四個藥水id 有 WZ 名字與價格，**哪個等級帶給哪一瓶**是選擇（`test/drop.test.ts` 釘住）|
| `DROP_LIFETIME_MS` | 300000 | 掉落物多久消失（`0x44 kind 0`）|
| `DROP_SPREAD_PX` | 24 | 掉落物離怪物的水平擴散 |
| `PICKUP_RANGE_PX` / `PICKUP_RANGE_Y_PX` | 40 / 60 | 「站在上面」的判定範圍 |
| `MOB_RESPAWN_MS`（§4.17）| 5000 | 怪物重生時間 |

**理由**：
1. **原值不可得，但行為必须可玩**：完整 MMO（ADR-001）需要掉落與經濟迴圈才能玩下去；把這些
   參數散在程式各處，之後就算量到真值也不知道要改哪裡、改完對不對。
2. **每一項都能被單獨量測**：ADR-004 的實機 run 只要抓一份真實流量，就能對照「掉落率／壽命／
   擴散距離／可撿範圍」四個常數，改成量到的值、跑同一組測試（`drop.test.ts` 的機率斷言用注入的
   亂數源，不依賴真隨機）。
3. **`DropPolicy` 是注入的**：`DropField` 接受 `policy`／`random`／`lifetimeMs`／`spreadPx`／
   `pickupRangePx`，所以「換一份掉落表」不需要動 `DropField` 或網路層，測試也不必碰真隨機。

**後果**：
- 任何時候看到這些數字，都應該假設「這是我們選的，不是解出來的」；`FINDINGS §4.18.8` 與
  `server/README.md` 都這樣寫。
- client 的 메소 顯示**不會**跟著變（`MesoWallet` 是伺服器端帳）：能力值區塊裡沒有已證實的錢欄位，
  而 `0x0D` 的 19 個 bit 裡也確實沒有錢（§4.21 解出後可以確定「不是漏送」）。這是已知缺口，不是 bug。
- 掉落物目前是**每個連線一份**（跟 `MobField` 一樣，ADR-001 的共享世界還沒做）：
  兩個玩家會各看到自己的掉落物。共享世界的 Phase 2 要把 `DropField` 跟 `MobField` 一起搬到
   per-field registry。

## ADR-008：怪物 AI 屬於 client（照 2003 年的分工），伺服器只轉播與記帳

**日期**：2026-10-16 ｜ **狀態**：已定案（可再評估）

**決策**：重寫的 client **要自己實作怪物的 AI**——per-mob 的狀態機（`sub_4862C0` 的角色）、
攻擊挑選（`sub_487D10`：`conMP <= MP`、矩形／線段命中測試、從命中清單隨機挑一個）與命中影格
（`sub_487A30`）。伺服器**不模擬怪物 AI**：它把 `0x33`／`0x35` 轉播給其他 client、接受
client 用 `0x2C` 回報的怪物動作（FINDINGS §4.20）。`0x0D` 解出之後（§4.21／ADR-009），
伺服器**只**用它送經驗值與升級補血；「被怪物打 → 掉血」仍然沒有驅動者。

**理由**：
1. **這是 binary 的分工，不是我們的偏好**：`sub_4862C0` 是 `CMob` 的 per-frame virtual，
   它在自己的程序裡挑攻擊、算傷害、把效果打在 `*(mob+108)` 這個使用者物件上，然後才送 `0x2C`。
   2003 年的伺服器看到的是「結果」，不是「決策」。把 AI 搬到伺服器等於**發明**一套協議，
   與 `GODOT_MIGRATION_PROMPT.md` 的證據優先順序衝突。
2. **與 ADR-006 一致**：傷害已經由攻擊方的 client 算（怪物→玩家是另一條同樣的迴路），
   伺服器的責任是記帳與權威狀態（誰在場、還剩多少 HP、什麼時候重生），不是重算。
3. **重寫的 client 本來就要有這套程式**：`CMob::Update` 同等物屬於 Phase 3/4 的 client 工作
   （ROADMAP），它需要的資料（`Mob/<id>.img` 的 `attack<i>/info`、`info.speed`、動作表）已經在
   `game/mobs.ts` 與 `protocol/mob.ts` 裡有讀取器。

**後果**：
- `serve --game-port` 目前自己送 `0x33` 讓怪物巡邏：那是**我們 client 還沒有 AI 之前的替代品**，
  不是最終架構。它與原 client 放在一起會有兩個驅動者（原 client 自己也會走），
  所以 oracle run（ADR-004）時要記得這件事，不要把它當成協定錯誤。
- 怪物攻擊玩家的**可見**部分（怪物播攻擊動畫、玩家的 HP 條下降）需要 `0x0D`（能力值差異包）
  才完整 —— `0x0D` 現在已解出並用於經驗值／升級（§4.21），但**扣血那條路徑仍然只有 client 的
  回報**：`serve` 收到 `0x2C` 只寫日誌，不會改玩家的 HP（§4.20.6 第 5 項）。
- ROADMAP 的「怪物 AI 與重生」從「伺服器工作」改列為 **client 工作**；伺服器那一側的對應項目是
  「`0x2C` 的記帳與 `0x35` 的轉播」。

## ADR-009：經驗值／升級用 client 自己的表；升級的成長量先不送（缺口要看得見）

**日期**：2026-10-16 ｜ **狀態**：已定案（可再評估）

**決策**：`0x0D`（能力值差異包）解出之後（FINDINGS §4.21），伺服器驅動「殺怪 → 經驗值 → 升級」這一條迴圈，
規則如下：

1. **門檻是 client 自己的公式**：`server/src/game/exp.ts` 的 `expToNextLevel` 逐行照抄 `sub_4C7110`
   （1–5 `n(n²/2+15)`、6–50 `q(q+19)`／`q=n²/3`、51–200 ×1.0548、`>200` 封頂 `0x7FFFFFFF`），
   不是我們挑的曲線。與公開的 2003 表比對 **196/200 相同**，四個差異是複本打字錯誤
   （用我們的值，前一級與後一級都能推回表上的數字）。這張表**只在 client 啟動時算出來**，
   `.data` 裡沒有靜態複本，所以它以公式而不是資料的形式存在。
2. **經驗值量是怪物自己的 `info.exp`**（`Mob/<id>.img`，已經在 `mobTemplateProvider` 裡），
   不是伺服器決定的係數。
3. **升級的成長量（`maxHp`／`maxMp`／`ap`／`sp` 加多少）先不送**：原伺服器的職業／等級成長表
   不在 client 裡（`sub_4C71C0` 這支「就地升級」routine 只扣經驗值、等級 +1、補血、重算傷害範圍，
   沒有任何成長量）。**發明一組數字比留著缺口更糟**（`GODOT_MIGRATION_PROMPT.md` 禁止發明規則），
   所以 `awardExp` 只送真的有變的欄位（`exp`／`level`／滿血的 `hp`／`mp`），角色的最大值維持不變，
   並在 FINDINGS §4.21.6 與 ROADMAP 標明這是**已知缺口**。
4. **升級要補滿 HP／MP**：這是 client 自己那支 routine 的行為（`sub_4C71C0`：還活著才補），
   伺服器照著做，否則玩家的經驗條會跳、血條不會動。

**理由**：
1. **單一來源**：門檻、升級行為、補血都在 `game/exp.ts`；以後無論是實機量到成長表、或是換一份
   職業成長表，都只動這一個檔案（`net/loginserver.ts` 只呼叫 `awardKillExp`）。
2. **可測**：公式是純函式（`test/exp.test.ts` 用公開表與邊界值釘住），升級／補血用假的角色紀錄測，
   殺怪 → `0x0D` 的那一段用真 socket 測（`test/serve.test.ts`）。
3. **差異包是「有變才送」**：`diffStats` 比較送出前後的紀錄，所以升級只多送 `level`／`exp`／`hp`／`mp`
   四個欄位，不會把整份 47-byte 身體塞進封包——這也是 `0x0D` 存在的理由（§4.21.1）。

**後果**：
- 升級後角色的 `maxHp`／`maxMp` 不變：**打同一隻怪會越打越慢**，這是預期行為，不是 bug。
- ADR-008 的「伺服器不改玩家的 HP」只對了一半：HP **現在會**由伺服器改（升級補滿），
  但「被怪物打 → 扣血」仍然沒有驅動者（`0x2C` 只是 client 的回報）。
- 能力面板的 buff 區塊（`panelFlags != 0`）仍然沒送，伺服器一律送 0。

## ADR-011：NPC 的台詞是 archive 的，線上是 CP949

**日期**：2026-10-16 ｜ **狀態**：已定案（可再評估）

**決策**：`0x47`／`0x15` 解出之後（FINDINGS §4.23），NPC 對話的行為如下：

1. **台詞是資料**：要說的話來自 `Npc/<7 位 id>.img -> info/speak`（數字鍵的 property 清單），
   不是寫在程式碼裡的字串表。`info/quest`（例如 `begin5`／`rina`）**原樣帶著、不解釋**：這個
   client 沒有任務 UI，`0x46`／`0x48` 也沒有 handler，所以「腳本名要做什麼」沒有可對照的行為。
2. **沒有 `info/speak` 就沒有對話**：NPC 的圖片裡沒有台詞清單時（出貨資料的
   `메이플운수 중형택시` 就是），點擊只回 `0x19`，不送一個空白的 `0x47`。
3. **一次只講一句**：每一句是一個 `0x47`，玩家按下主要按鈕（`answer == 1`）才送下一句，其他結果
   （第二個按鈕／ESC／關窗）就結束；對話進行中再點 NPC 只回 `0x19`（`CQuestMan+4` 會讓 client 對
   第二個 `0x47` 丟例外）。
4. **字要送出去就得是 CP949**：封包字串是 `u16 長度` + 原始 bytes，client 直接當系統 ANSI 字碼頁
   的字用。`protocol/cp949.ts` 提供編碼，**編不出來的字元丟例外**，不送出去變亂碼。

**理由**：

1. **與 ADR-010 同一條原則**：能用資料的地方就不要寫死。台詞在 `Data.wz` 裡、長度與按鈕是 binary
   的事實，兩者都不需要我們的創意；只有「點 NPC 之後先講第一句、按下去講下一句」是我們的流程選擇
   （原伺服器的 NPC 是腳本，腳本不在手邊）。
2. **CP949 是契約不是細節**：ASCII 以外的字一旦編錯，client 畫出的是亂碼 —— 那是「有送出但玩家看不懂」
   的靜默錯誤，比丟例外糟得多。丟例外會在任何測試裡立刻現形。
3. **`0x15` 的 `answer` 語意要留紀錄**：`1`／`0`／`0xFF` 是五個 handler 各自的映射（`0x2001`→1、
   `0x2000`→0、ESC→`0xFF`），不是一個通用的 enum；所以常數放在 `protocol/quest.ts` 並在
   `QUEST_ANSWER` 的註解裡寫明來源，而不是散在各處的魔術數字。

## ADR-010：商店的價格來自資料、庫存來自我們；mesos 只有一份（角色紀錄）

**日期**：2026-10-16 ｜ **狀態**：已定案（可再評估）

**決策**：`0x4A`／`0x4B`／`0x16`／`0x33` 解出之後（FINDINGS §4.22），NPC 商店的行為如下：

1. **mesos 只有一份**：`CharacterData` 的第 22 欄（`stats.mesos`，記憶體 `+89/+93`）就是錢。
   `game/rewards.ts` 的 `MesoWallet` 是**那份紀錄的視圖**（`new MesoWallet(character.stats)`），
   不是第二本帳；任何改動都用 `0x0D`（旗標 `0x40000`）送給 client。
2. **價格是資料**：每一列的 `u32 price` 來自該道具自己的 `info/price`
   （`Item/Consume/0200.img/<id>/info/price`，`game/shops.ts` 的 `itemPrice`）。
   讀不到價格的道具**不會被放進商店**（列不會被送），而不是送一個 0 讓 client 印出來。
3. **庫存是我們的選擇**：2003 年的商店是伺服器上的腳本，`Data.wz` 裡沒有任何商店資料，
   所以「哪個 NPC 賣什麼」（`SHOPS`）、一次能買多少（`DEFAULT_SHOP_MAX_COUNT`）、
   賣回給商店拿多少（`SELL_PRICE_RATIO`）都是這份 repo 的決定，集中在 `game/shops.ts`，
   並由 `test/shops.test.ts` 釘住。兩個商店掛在**地圖 `life` 裡真的存在**的 NPC 上
   （`1010100` 리나／헤네시스、`2003` 로빈／달팽이사냥터）。
4. **回覆契約照 client 的規則**：買／賣／充電**一定**回一個 `0x4B`（`dlg+184` 是 client 的鎖，
   只有 `0x4B` 解得開）；關窗**不回**（那時 `dlg+184 == 0`，回下去 client 會自己丟
   `CDisconnectException`，FINDINGS §4.22.3）。
5. **207 家族不賣**：那 8 bytes 的長度確定、內容未知，codec 只攜帶不產生（§4.22.2）。

**理由**：
1. **能算的不要抄**：`info/price` 是檔案裡的事實，抄一份到程式碼就會漂移；庫存反過來是
   檔案裡不存在的東西，只能寫下來並標成選擇 —— 兩者分開，未來才分得清「這行是證據」
   還是「這行是我們決定的」（與 ADR-007 同一條原則）。
2. **金額只有一處**：舊設計的 `MesoWallet` 自己記帳、紀錄裡另有一份，兩者靠呼叫端同步；
   改成視圖之後，「client 顯示的錢」與「伺服器的錢」在型別上就是同一個物件。
3. **client 的兩條例外是契約，不是細節**：不回的 `0x4B` 會讓玩家的視窗卡死、多回的 `0x4B`
   會讓 client 斷線 —— 兩件事都寫在 `handleShopRequest` 的註解與測試裡。

**後果**：
- 商店的**內容**要改，改 `game/shops.ts`；要換一份價格來源，改 `itemPrice`。網路層不變。
- 撿到錢、買東西、賣東西三條路徑現在都會送 `0x0D` 的 `0x40000`，畫面上的錢包會跟著動。
- 裝備還不能賣（這一版 `Item/` 底下沒有裝備圖，`Character/<type>/<id>.img` 的價格外加規則
  沒有證據）；`0x16` 的充電（op 2）沒有實作，一律回「東西不夠」。
- NPC 的對話與任務：`0x47`／`0x15`（NPC 對話，FINDINGS §4.23）由 **ADR-011** 接手；
  `0x46`／`0x48` 在 CQuestMan 的分派器裡**沒有 case**（`sub_4A58F0` 只把 71 交給 `sub_4A5910`），
  所以真正的「任務流程」不是還沒解的封包，而是**我們要自己定義的功能**。

## ADR-012：世界是「每張地圖一份」，玩家進出的是同一個 instance

**日期**：2026-10-16 ｜ **狀態**：已定案（可再評估）

**決策**：伺服器的世界階層固定為 `FieldRegistry`（mapId → `FieldInstance`）：

1. **一個 mapId 一個 `FieldInstance`**，第一次有人進場時建立、**最後一個人離開後不刪**。
   怪物、NPC、掉落物、在場玩家全部屬於它，不屬於連線。
2. **連線只是「成員」**：`FieldMember`（`characterId`／`name`／`avatarItems`／`send`）是
   `FieldInstance` 對一個玩家的全部認識；socket 關閉＝`leave`，不是「這個世界結束」。
3. **廣播範圍照 client 的池子決定**（FINDINGS §4.24.1）：坐落在場地池子上的封包（`0x1C`／`0x1D`／
   `0x22`、怪物 `0x2F`–`0x35`、NPC `0x39`–`0x3B`、掉落 `0x43`／`0x44`）送給**場地裡的每個人**；
   動到某個人角色紀錄的（`0x0B`／`0x0D`／`0x11`、`0x16`）只送給那個人。
4. **一個時鐘**：`GameEntryServer` 只有一個 server-wide interval（`tickFields` 用 `FieldRegistry.instances()` 走過所有場地，每個場地一次 `FieldInstance.tick`）；
   原本「每條連線一個 `setInterval`」造成的「同一隻怪在兩個人螢幕上走不同的路」隨之消失。
5. **`FieldInstance.tick` 只在有人看的時候走路**：沒人看的場地不派 `0x33`，但屍體／重生計時與
   掉落物過期照算 —— 世界比連線長壽，離線期間發生的事仍然發生。
6. **角色 id 全伺服器唯一**（`nextCharacterId(accounts)`）：`CUserPool` 以 id 為 key，
   兩個帳號各自從 1 起算會在同一張圖撞 id，而 client 的自我排除會**安靜地**吃掉那筆進場紀錄。
7. **不刪場地、不廣播給離線者、snapshot 只補活著的怪物**都是**我們的選擇**，集中在 `world.ts` 一處。

**理由**：
1. **ADR-001 的「完整 MMO」就是這一條**：不是「一個 socket 一個世界」。玩家 A 打死的怪必須對 B 也死了，
   否則所有權（誰的血、誰的掉落物）會在第一次連線進來時就崩掉。
2. **所有權只有一處**：`MobField`／`NpcField`／`DropField` 原本掛在 socket 的 session 上，
   等於「每個玩家一份世界」；搬到 `FieldInstance` 後，「這隻怪的血」只有一個數字。
3. **擴充點是資料結構而不是 if**：頻道／分流只要把 registry 的 key 從 `mapId` 改成 `(mapId, channel)`；
   換圖只要 `leave` ＋ 另一個 `of(mapId).join` —— 沒有連線層的知識。
4. **最省事的實作就是最不容易壞的實作**：成員只有一個 `send` 函式，廣播＝走過成員；
   沒有 event bus、沒有 per-socket 狀態複本（§4.24.3 說明了「填 0 是安全的」那幾個欄位）。

**被否決的選項與原因**：
- **每條連線一份世界（現狀）**：實作最簡單，但它不是 MMO，而且越晚換越貴。
- **全域單一 `Field`（不分地圖）**：`0x16` 的換圖語意會消失。
- **把場地在最後一個人離開時刪掉**：重登會看到一張「剛開機」的圖（怪全在、掉落物全沒）；
  留著記憶體成本上限＝地圖數，換來「世界是持續的」。

**後果**：
- `net/loginserver.ts` 不再自己持有 `MobField`／`NpcField`／`DropField`，只持有 `instance` 與
  「我這個成員」；NPC／怪物的生成只發生一次（`spawnAll`），不再每位玩家一次。
- `0x1C`／`0x1D`／`0x22` 的 sender 只在 `game/world.ts`，`protocol/field.ts` 保持純 codec。
- 測試必須是**假成員**（`test/world.test.ts`）：真的 socket 保留給「兩條連線真的互相看見」的煙霧測試。
- 未實作的部分照 FINDINGS §4.24.9 掛著：`0x1C` 的三個欄位語意未解、頻道還沒做。
  （`0x29`（別人升級的特效）後來解掉並實作了 —— ADR-015／FINDINGS §4.27。）

## ADR-013：換地圖的目的地與落點都來自地圖資料；`mode` 未解之前落點是出生點

**日期**：2026-10-16 ｜ **狀態**：已定案（落點那半可再評估）

**背景**：`0x0D`（`s32 kind` ＋ `string name`）在 §4.11.6 就解出來了 —— 玩家用了一個傳送門，
client 送的是「滑鼠下那個東西的名字」。伺服器要回答 `0x16`。但**封包裡沒有地圖 id、沒有座標**。

**決策**：

1. **目的地查地圖資料，不從封包猜**：拿 `name` 在**當前地圖**的 `portal` 清單裡找同名的那一個，
   用它自己的 `tm`（to map）。封包裡沒有地圖 id，所以任何「從封包讀目的地」的實作都是發明。
   `tm = 0`（或 `999999999`）＝這個傳送門不連去別張圖 ⇒ 只記日誌。
   名字比對**不分大小寫**（名字是資料；大小寫不該決定傳送門有沒有作用）。
2. **每一個 `0x0D` 都回一個空的 `0x19`**，包含「這個名字不是本圖的傳送門」與「`kind` 不是 -1」：
   client 送完 `0x0D` 就把互動閘門鎖上（`sub_472590` 的 `n3000[6]`），只有 `0x19` 解得開
   （`sub_4728B0`）。不回＝玩家之後再也按不了任何東西。所以 `0x19` 在讀封包**之前**送。
3. **換圖的四步順序**：目的地先建好（建不出來就留在原地）→ 離開舊場地（`0x1D` 給還在的人）→
   `0x16` → `join`（新場地的快照）。理由見 FINDINGS §4.25.3：`CUserPool` 以角色 id 為 key，
   同一個人不能同時在兩張圖；而 client 要先有場地物件才裝得下新場地的封包。
4. **落點 ＝ 目的地的出生點**（`sp` 傳送門 → 第一個 `pt = 0` → 第一個傳送門，再取腳踏點），
   `mode` 一律送 `0`。**`tn`（目的地那一側的傳送門名字）只用於日誌**：`0x16` 沒有座標，
   落點是 `mode` 的語意，而 `mode` 沒有定位（§6 第 2 項）—— 猜一個沒驗證的值等於把猜測寫進協議。
   等 oracle run 之後，要改的只有 `spawnPointOf`／`FieldInstance.spawnAt` 一個地方。
5. **「登入在哪張圖」是角色紀錄自己的事**：紀錄的 `stats.mapId != 0` 就進那張圖（換圖會改寫這一格，
   所以下線在哪上線就在哪）；`0` 才用 `--map`。`--map` 因此同時是「新角色的起始圖」
   （`LoginServer.startMapId`）與「沒有 mapId 的紀錄的後備」（`GameEntryServer.mapId`）。
6. **商店與對話跟著換圖清掉**（視窗屬於舊圖的 NPC，client 重建場地時自己會收），**場地不刪**
   （沿用 ADR-012：世界比連線長壽）。同圖的傳送門走同一條路（離開再進入），沒有特例。

**被否決的選項與原因**：
- **等 oracle run 再做傳送門**：`0x0D` 的形狀、`0x19` 的義務、`tm`／`tn` 都是既有證據，
  剩下的未知只有落點；整條路做出來之後，oracle run 只要回答一個欄位，而不是一個功能。
- **猜一個 `mode` 讓玩家落在 `tn`**：`tn` 的座標在目的地查得到，看起來很吸引人，但 `mode` 的語意
  沒有證據；猜錯的症狀（玩家站在牆裡／掉出地圖）比「站在出生點」難查得多。
- **接受封包裡的地圖 id**：`kind != -1` 的那條路是 GM 的 `/헉맵`（§4.11.6），
  把它當成一般玩家的換圖請求等於開一個沒有證據的後門。
- **換圖時重建 session**：session 記的是「這個人」而不是「這條連線在哪張圖」，
  重建只會把錢包與角色紀錄的來源搞成兩份。

**後果**：
- `--map` 的說明要說清楚：它現在是「新角色的起始圖 ＋ 沒有 mapId 的紀錄的後備」。
- 換圖之後 `session.at`、`character.stats.mapId`、商店／對話都由 `enterMap` 一處更新。
- 想做「用傳送門落點」時，唯一要動的是 `game/world.ts` 的 `spawnPointOf`。
- 未實作（誠實）：頻道／分流、傳送門的條件（等級／道具）、`pt` 的種類語意、`kind != -1`。

## ADR-014：聊天是「轉播＋回音」，文字以 bytes 轉送，名字是伺服器的

**日期**：2026-10-16 ｜ **狀態**：已定案

**背景**：`0x12`（client → 說一句，一個字串）在 §4.13 就列出來了；§4.11.6 也記了 `0x1A` 這個
「使用者訊息」家族，但把它整個當成密語。§4.26 把其中 sub-op `0x12` 解到欄位層：`str 名字` ＋
`str 內容`，client 排版成 `名字>> 內容`（聊天視窗開著時加一行，關著時自己組一個氣泡封包）。
同時確認了一件事：**client 的聊天輸入只送不顯示**（`sub_470C70` 組完封包就結束，`%s>> %s` 的排版
只存在於接收端 `sub_472910`）。

**決策**：

1. **伺服器轉播給全場，而且包含說話的人**。不含說話的人會讓玩家永遠看不到自己說的話（client 沒有
   本地回顯）；這不是禮貌問題，是正確性問題。
2. **文字以 bytes 原樣轉送**（`UserChat.text`／`ClientChat.text` 是 `Uint8Array`）。伺服器是轉播者，
   不需要讀那行字；而「解碼再編碼」是唯一會弄丟字元的一步（`cp949.ts` 對編不出來的字元丟例外）。
   要給人看的解碼只發生在 log（`describeUserChat`）。
3. **名字由伺服器自己填**（`session.name`）。`0x1A` 裡**沒有角色 id**：接收端的 client 只需要一個名字
   （要畫在誰頭上是它自己用名字查的），而伺服器當然知道是誰在說話。
4. **聽眾是場地**（`FieldInstance.broadcast`）：`0x1A` 是 `CField` 自己的 opcode，所以「同一張圖」
   就是聊天的範圍，換圖就換聽眾。沒有頻道／分流這種第二層 key。
5. **只做聊天那一個 sub-op**。`0x09`（找人回報：`str 名字` ＋ `u32 mapId`，`-1` ＝ 找不到）、
   `0x0A`（自己送出的密語的投遞結果：`str 名字` ＋ `u8`）、`0x22`（對方拒收密語：`str 名字`）的
   讀取形狀已解出，但這台伺服器沒有密語系統、也沒有找人指令，所以**不做 codec、不動玩家**
   —— 沒實作的就不猜（`0x0D` 的 `kind` 是同一條規矩）。
6. **文字不解析、不過濾**：`/` 開頭的指令（`sub_470E10` 的 GM 家族）不在這裡實作，2003 年的 client
   本來也沒有過濾。伺服器只轉播它收到的 bytes。

**被否決的選項與原因**：
- **把 `0x1A` 當成「CWvsApp 層 opcode 的包裝」**：sub-op 值域 9..34 與 §4.10 那張表重合（`0x12`
  在兩邊都出現），看起來很像，但兩邊的**讀取形狀不同**（那張表的 `0x12` 是 인기도：`u8 type` ＋
  `str name`；這裡的 `0x12` 是兩個字串）。沒有共同來源的證據，所以不這樣命名。
- **在伺服器上解碼再編碼聊天文字**：多一次有損轉換，換來的是伺服器「看得懂」一行它不需要看的字。
- **只送給別人（不回音）**：等於要求 client 自己印自己的話，而它不會。

**後果**：
- `field.ts` 有三個新 codec（`readClientChat`／`encodeClientChat`／`describeClientChat`、
  `readUserChat`／`encodeUserChat`／`describeUserChat`），`USER_MESSAGE_CHAT` 是唯一實作的 sub-op。
- 之後要做密語或 `/찾기`，`0x09`／`0x0A`／`0x22` 的形狀已經在 FINDINGS §4.26.2 的表上。
- 測試上多了一條規矩：**「之後什麼都沒發生」不能再用 `FakeClient.take(0)` 斷言**（它永遠成立），
  要用 `drain()` 收一段時間再過濾（§4.26.4 的註）。

## ADR-015：升級特效只送給別人（升級的人自己已經播了）

**日期**：2026-10-16 ｜ **狀態**：已定案（「不送給自己」那半是推論，列在 FINDINGS §6）

**背景**：`0x0D`（§4.21）的升級分支會讓**升級的人自己的 client** 播
`Effect/BasicEff.img/LevelUp` ＋ `LevelUp` 音效（`sub_55BEB0` 的尾端，`.c:352616`）。§4.27 把
`0x29` 解出來：它是 `u32 characterId`（由 `sub_51D590` 讀、在 `CUserPool` 裡查，**查不到就整包丟掉**）
＋ `u8 effect`，`effect = 0` 是**同一組**資源、用 `sub_50D6D0(user)` 建在那個人身上。

**決策**：

1. **升級時廣播 `0x29 {characterId, 0}`，排除升級的人**（`FieldInstance.broadcast` 的第二個參數）。
2. **只認 `effect = 0`**：`1` 後面還有一個 `u32`，語意未解，所以 codec 拒絕非 0 的值（`RangeError`），
   與 `0x1A` 的非聊天 sub-op 同一條規矩。
3. **放在 `awardKillExp`**：等級是那裡變的（`gain.levels > 0`），順序是「先 `0x0D` 給升級的人、
   再 `0x29` 給其他人」，兩個都是同一個同步處理常式裡的事。

**被否決的選項與原因**：
- **也送給升級的人自己**：兩條路都會建一個新的效果物件（`sub_50D6D0` 沒有去重），送兩次就是把同一個
  特效疊兩層。除非 oracle run 證明原伺服器就是這樣送，否則不這樣做。
- **完全不送**（現狀）：別人看不到你升級 —— 這是 §4.21 就記下的缺口，現在有證據可以補。
- **猜 `effect = 1`**：不知道它做什麼，不猜（不送、不實作）。
- **廣播給全場（含升級者）後靠 client 去重**：client 沒有這種邏輯。

**後果**：
- 升級這件事現在有兩個封包、兩個方向：`0x0D`（自己的數字）與 `0x29`（別人的眼睛）。
- `0x29` 的 id 會被接收端的池子過濾，所以「廣播給一張圖」是安全的（不知道的 id 等於沒送）。
- 剩下的未知：`effect = 1`、「不送給自己」的推論、以及實機驗證（ADR-004）。

## ADR-016：NPC 的走動是 client 的，**政策**才是我們的（預設：沒人走）

**日期**：2026-10-16 ｜ **狀態**：已定案（政策本身是我們的選擇，機制有證據；未定的部分列在 FINDINGS §6）

**背景**：`0x3B` 從 §4.19 起就掛著「第二狀態，可能是走動或表情」。§4.28 把它結掉：對一個池裡已經有的
id，flag 只有一個下場 —— `sub_499760(vecctrl, flag)`：`1` 用 vtable 第 184 槽開始走（四個 `s16`＋方向＋
foothold，之後 `rand() % 8000 + 4000` ms 重挑一次目標），`0` 是七個 0（停）。也就是說
**2003 年的 NPC 是 client 自己走的**，伺服器只負責說「這個要走」。

**決策**：

1. **送 `0x3B`，不模擬走動**：`game/npcs.ts` 的 `walk` 政策決定哪些模板要走，伺服器只送那個封包（
   `NpcField.enterPackets()` 讓它緊跟在 `0x39` 之後），**不記 timer、不算座標**。client 自己會在
   4–12 秒後重挑目標 —— 重做一遍等於把同一件事寫兩次，而且兩邊的隨機不會一樣。
2. **政策是一個輸入，不是寫死的表**：`--npc-walk <none|all|id,id,...>` → 一個
   `(templateId) => boolean`；解析不了的值讓伺服器**起不來**（`RangeError`），不是安靜地什麼都不走。
3. **預設 `none`**：機制（client 自己走）有證據，**哪些** NPC 該走沒有 —— 那是原伺服器的選擇。預設值
   是唯一的「誠實」選項：不能證明就不做。同 ADR-015 的規矩。
4. **狀態是場地快照的一部分**：新進場的人在該 NPC 的 `0x39` 之後收到同一個 `0x3B`，所以「誰在走」不
   需要任何額外的補送邏輯（`FieldInstance.join` 已經在送 NPC 清單）。
5. **`setWalking` 與 client 一樣是冪等的**：同一個狀態不發封包（`sub_49F260` 在 bit 已設時直接回傳）。
6. **怪物那一側不動**：§4.28.3 順手定位到 `0x31` flag 1 會讓原 client 自己走那隻怪
   （`sub_485330`），但我們的伺服器是**每條腿一個 `0x33`** 的權威模式（ADR-008 的例外，§4.24）。改成
   client 自己走等於放棄多人同步的權威，所以**不改**；兩者會不會互相打斷列進 FINDINGS §6 第 14 項，
   由 oracle run 回答。

**被否決的選項與原因**：
- **用 `0x3D` 送走動**（伺服器指定動作＋可選的 `CMovePath`）：那個 `CMovePath` 只在**模板的一個旗標**
  非 0 時才在封包裡，而旗標的 WZ 來源未定位 —— 長度猜錯會讓 client 把後面的位元組當移動路徑解。
  等 §6 那題有答案再說（索引那半已經解了：`sub_499C00` ＝ 播一個動畫）。
- **在伺服器模擬 NPC 走動**：沒有「移動一個 NPC」的封包（`0x33` 是怪物的），而 client 自己就會走；
  模擬只會多一份不同步的狀態。
- **預設 `all`**：會在每一張圖做出一個我們無法證明的行為（40 幾個 NPC 一起晃）。
- **把「哪些 NPC 走」寫死成一張表**：那張表的來源只能是猜測；`--npc-walk` 至少把選擇留在外面，
  等 oracle run 之後把它變成資料。

**後果**：
- NPC 的走動是**開關式**的：一個封包、零 timer、零狀態機，`0x3A` 或 `flag 0` 就結束。
- 「NPC 會走動」在 README 的誠實聲明裡從「沒有」變成「有，但預設關著，因為不知道該 who」。
- 剩下的未知集中在兩個地方：**哪些 NPC**（政策）與**原 client 自己的走動與我們的 `0x33` 的關係**
  （怪物那一側），兩者都在 FINDINGS §6 第 14 項，等 ADR-004 的 oracle run。

## ADR-017：角色存檔 —— 檔案就是整個世界，讀不懂就拒絕啟動

**日期**：2026-10-16 ｜ **狀態**：已定案（格式與時機都是我們的設計；沒有封包可比對，見 FINDINGS §4.29）

**背景**：到這個 ADR 之前，帳號與角色只在記憶體裡（`net/loginserver.ts` 的檔頭自己寫著這件事），
所以重啟就忘掉一切，「明天再上線」這件事根本不存在 —— 而 ADR-001 的目標是**完整 MMO**。協定裡沒有
存檔封包可比對：client 只在登入的 `0x03`（角色清單）與進場的 `0x16` **收到**一份 `CharacterData`，它的
c2s 送包裡沒有任何一封帶角色資料（FINDINGS §4.29）。也就是說「什麼時候存、存什麼格式」跟掉落機率
（ADR-007）與商店價格（ADR-010）同一類：**是伺服器實作自己的選擇**，只是這次的選擇會決定「會不會弄丟
玩家的角色」，所以標準比那兩者高。

**決策**：

1. **一個 JSON 檔就是整個世界**：`{ version, accounts: { <帳號>: { password, characters: [...] } } }`，
   角色的 stat 區塊與道具區塊都在裡面（`game/save.ts`）。選 JSON 是因為它是人可以讀、可以 diff 的形狀，
   而存檔是**要活很久的資料**；角色只有三個、一次存檔是幾 KB，省那幾個 byte 換不到任何東西。
2. **介面只有兩個方法**：`SaveStore.load()`／`save(accounts)`。`FileSaveStore` 是產品用的一個檔案，
   `MemorySaveStore` 給測試（它保存的是**文字**不是活著的表，所以「存過什麼」與後來的改動無關）。
   `LoginServer`／`GameEntryServer` **不知道檔案存在**，它們只拿到一個 `persist()` 回呼。
3. **寫入是原子的，而且整表重寫**：先寫 `<path>.tmp` 再 rename 蓋過去。崩潰只會留下「前一個版本」，
   不會留下半個檔。整表重寫在這個尺寸下是對的：檔案小、變動最多幾秒一次，而且**只有一個檔案**要嘛是
   舊的、要嘛是新的，沒有第二個地方可以不一致。寫入失敗**不丟例外**（它跑在 socket 的事件處理裡），
   只留一行日誌。
4. **讀不懂就拒絕啟動**：版本不合、不是 JSON、角色缺 `id`／`name`、兩個角色共用一個 id、或紀錄根本
   **送不出去**（用 `writeCharacterData` 試編一次）→ **throw**，`cli.ts` 印出來並以 1 結束。理由是
   這個方向只有一個失敗模式會真的弄丟角色：伺服器起成**空的**世界，然後第一次存檔把空的世界寫回去。
   「檔案不存在」是唯一的例外（第一次執行）。
5. **檔案勝過 `--account`，而且會說出來**：`--account` 只是**第一次**執行時的種子；之後世界在檔案裡。
   不自動合併（合併需要一條「同名不同密碼」的規則），但會記一行「ignoring N --account entr(ies)」。
6. **存**真相**，不存衍生值**：`flags` 不入檔 —— 它是紀錄內容的函式（`characterDataOf` 推導），存它等於
   對同一件事留下第二個說法。載入時反過來推導一次，並用 wire codec 驗一次「這個紀錄 client 收得下」。
7. **`bigint` 用十進位字串**：現金道具的 `sn`／`unknown1A` 是 u64（`itemslot.ts`），JSON 沒有 64 位元
   整數，而四捨五入一個序號是**無聲的損壞**。
8. **存的時機是三個事件**：建立角色、刪除角色、**session 結束**（`socket.on("close")`）。第三個是關鍵：
   經驗值、等級、道具、錢、換過圖的 `mapId` 全都改在**登入伺服器交給遊戲伺服器的那一份紀錄**上，
   所以「下線時存一次」就是完整的存檔。不做每封包存檔：那會為了走一步路重寫整個檔案。
9. **一個角色一份紀錄**：`withMapId` 從「回傳一份淺複製」改成**直接用同一份物件**（缺 `mapId` 時就地
   填後備值）。這是接上持久化時發現的既存陷阱：淺複製讓 `stats` 與 `items` 分家，經驗值與等級會加在
   副本上，而存檔存到的永遠是進場前的那一份 —— 測試 17（`serve.test.ts`）就是為了釘住這件事。

**被否決的選項與原因**：

- **SQLite／二進位格式**：多一個相依與一個要學的格式，換到的是我們現在不需要的規模與併發。
  真的需要時，`SaveStore` 就是那個接縫（換一個實作，兩台伺服器都不用改）。
- **每個 mutation 都存**（每撿一個東西、每加一次經驗值）：寫入次數與「走一步路」的次數同量級，
  而且**還是**會丟掉當掉那一瞬間的記憶體狀態，只是丟得比較少。
- **存檔裡也存 `flags`**：見決策 6，那會製造第二個說法。
- **讀不懂時「盡量讀」**：半讀出來的帳號表比拒絕啟動危險得多，因為它會**被存回去**。
- **自動合併 `--account` 與檔案**：需要一條我們沒有證據寫的規則（誰的密碼對？誰的角色？）。
- **手改存檔當成支援的操作**：JSON 讀得懂是為了**除錯與 diff**，不是為了讓玩家改等級；`readSave` 會把
  改壞的檔案擋在門外（包含「client 收不下」的紀錄），而不是讓它進到線上。

**後果**：

- README 的誠實聲明從「沒有持久化（重啟即忘）」變成「有存檔，但當掉那場 session 會少掉最後幾分鐘」。
- 備份／搬移／複製一個世界 = 複製一個檔案；`--save off` 保留「以前的樣子」給純協定實驗。
- 格式變更要動 `SAVE_VERSION`（舊檔會被**拒絕**而不是被猜），所以任何改 `CharacterData` 的變更都要
  一起想一次存檔路徑。
- 尚未處理：同一角色同時被兩個 client 選走（兩邊共用同一份紀錄）、頻道化之後的「存檔屬於哪個世界」
  （目前 `--save` 是整個 process 一份）。

## ADR-018：一個帳號一條活著的 session（`0x08` 心跳 ＋ 一句「已在線上」）

**日期**：2026-10-16 ｜ **狀態**：已定案（機制有證據；間隔與逾時是我們的選擇）

**背景**：`0x01`／`0x02`／`0x03` 的 `result` 值表裡有一個 `7`，client 的訊息是
「현재 접속중인 아이디이거나,\r\n현재 서버점검중입니다.」（「這個帳號正在線上，或伺服器維修中」）。
那是**原 client 的設計**：同一帳號的第二條連線要被拒絕（FINDINGS §4.8 的修正）。在這個 ADR 之前，
本伺服器兩條都放進來，而兩條連線拿到的是**同一份 `CharacterData`**（帳號表裡的那個物件，ADR-017）——
於是兩個 client 會互相蓋掉對方的經驗值、道具與錢。使用者要的是完整 MMO（ADR-001），這是第一個
「兩條連線同時存在」就會壞掉的地方。

**決策**：

1. **座位是「帳號」的，不是「角色」的**：`OnlineAccounts`（`src/net/online.ts`）是
   `account → 活著的 session 集合`。拒絕的訊息講的是帳號（`0x01` 那一步），所以座位也在那個粒度上。
   「這個**角色**已經在圖裡」是另一個（更窄的）不變式，它住在角色真正在的地方：`GameEntryServer`。
2. **兩半各拿一次座位**：登入伺服器在 `0x01` 成功時拿、socket 關閉時還；遊戲伺服器在角色**進場**時拿、
   socket 關閉時還。兩半共用**同一份** `OnlineAccounts`（`cli.ts` 建立、傳給兩個 server，
   介面上是 `LoginServerOptions.online`）。因為換到遊戲伺服器是**另一條 TCP 連線**：只有登入那一半，
   玩家在選角畫面待多久就佔多久；只有遊戲那一半，則認不出「已登入、還沒選角」的帳號。
   兩半的座位互相重疊時，座位在**最後一條連線**結束時才釋放。
3. **拒絕就是 client 自己的訊息**：`0x01` 回 `7`（`LOGIN_RESULT.alreadyConnected`），日誌寫出
   **是誰在佔**（`login 10.0.0.9:53123 (32s), game 10.0.0.9:53140 (5s)`）—— 玩家申訴時操作者要的
   就是這一行。
4. **同一個角色的第二條連線獨立擋掉**：`GameEntryServer.sessionsByCharacter`；第二條直接關閉，
   第一條不受影響。擋的不是「重複的 id」（`FieldInstance.join` 會換掉舊成員），而是**舊的那條連線
   會活著但沒有人再看見它**：它還能走、能說話、能打怪，而且兩條連線寫同一份紀錄。刻意**不**用
   `0x07`（遷移）把它踢掉：那會讓舊 client 去連一個我們的登入伺服器不認得的位址。
5. **心跳用 `0x08`，因為它是 client 唯一保證會回的封包**：`sub_43B170` 在**看 stage 之前**就處理
   `0x07`／`0x08`（所以任何階段都能用），`sub_43B280` 只做一件事：讀一個 u32、原封不動送回去
   （FINDINGS §4.2／§4.30）。**任何**封包都算活著的證明（`note`），安靜超過一個間隔才由伺服器主動問。
6. **逾時就是斷線**：安靜超過 `timeoutMs` 的 session 直接 `socket.destroy()`，於是**所有既有的 close
   路徑照常執行**（座位歸還、`0x1D` 廣播、存檔）—— 沒有第二條「假裝下線」的路徑要維護。
   預設：間隔 30 s、逾時 3 個間隔（≈90 s），`--ping <ms|off>` 可調，`off` ＝不裝心跳。
7. **播下的 u32 沒有語意**：client 讀進來就送回去，沒有其他地方讀它（`sub_43B280`）。本伺服器送一個
   計數器，只為了讓自己的 trace 好讀；2003 年的伺服器送了什麼，client 裡沒有證據可比。

**被否決的選項與原因**：

- **不處理**（現狀）：兩個 client 共用一份角色紀錄，是 ADR-017 的直接漏洞，且使用者要的是完整 MMO。
- **每個角色一個座位**（在 `0x03` 選角時就鎖角色）：會在選角畫面誤鎖 —— 那一步只是把 id 交給 client，
  連線還沒到遊戲伺服器；而且它回答不了「同一帳號兩條連線選**不同**角色」的情況。
- **用 `0x07` 踢掉舊的連線**：`0x07` 的 `flag != 0` 是「去連另一個位址」，而那個位址屬於原伺服器拓樸；
  我們的登入伺服器不認得它（見決策 4）。
- **靠 TCP 自己發現斷線**（不用心跳）：半開的連線可以撐很久，而那個帳號在期間內是**被鎖住**的
  （訊息還說著「你已經在線上」）。心跳是唯一能讓訊息說謊時間變短的工具。
- **心跳太密**（例如 5 s）：每個閒置連線每分鐘 24 個封包，換來的是「快 25 秒發現」，不值得。
- **逾時太短**（例如 1 個間隔）：慢的網路／忙碌的 client 會被誤判成斷線，而斷線是有破壞性的動作
  （清掉座位、廣播 `0x1D`、存檔）。

**後果**：

- README 的誠實聲明拿掉「沒有『已在線上』的處理」；換上「有座位，號碼是我們的選擇」。
- 這兩個號碼（30 s／90 s）是**未驗證的伺服器行為**，與掉落機率（ADR-007）、商店價格（ADR-010）
  同一類：等 oracle run 有真實流量時可以量。
- 頻道化（ADR-013 的下一步）會把「誰在線上」的範圍從「一個 port 一個世界」變成「每個世界／頻道」，
  那時 `OnlineAccounts` 要跟著分割 —— 它的介面只有四個方法，就是為了那時候好換。

## ADR-019：密語與找人用「名字」定位玩家，而且只有線上的算數

**日期**：2026-10-16 ｜ **狀態**：已定案（形狀全部有證據；「線上才算」與大小寫規則是我們的選擇）

**背景**：`0x23`（`sub_4717D0`）是 client 對**一個名字**的請求，`0x1A` 的 `0x09`／`0x0A`／`0x22` 是它的
三種回覆（FINDINGS §4.31）。這是本伺服器第一個「目標不在寄件者所在場地」的封包，因此需要一個
**名字 → session** 的查找，也需要回答幾個 client 沒有明說的問題：離線的人算不算找得到？大小寫怎麼算？
拒收怎麼辦？這一節把這些定下來。

**決策**：

1. **查找是掃 `sessionsByCharacter`，不另建索引**。那份 map 已經是「誰在線上」的唯一真相
   （ADR-018 用它擋第二條連線），名字查找只是走一遍 Value（線上人數的量級）；多一個 `name →
   session` 索引就多一份要與它同步的狀態。`sessionNamed` 是唯一的入口。
2. **「線上」就是唯一的條件**：沒有活著的 session 的角色，`0x09` 回 `0xFFFFFFFF`、`0x0A` 回 flag 0 ——
   兩個都是 client 自己就有的「找不到」訊息（`'name'님을 찾지 못했습니다`）。**刻意不回存檔裡的地圖 id**：
   那是「上次下線的地方」，而 client 的訊息說的是「現在的位置」；離線的人沒有現在的位置。
3. **大小寫不敏感，但回覆用存在的那個拼法**。角色建立時 `nameTaken` 就是忽略大小寫在擋重複的
   （ADR-017 的存檔格式不變），所以忽略大小寫的查找不可能挑錯人；而回給 client 的名字一律用**紀錄裡的**
   拼法，別人看到的才是角色真正的名字（打 `alt` 找到 `Alt`，畫面顯示 `Alt`）。
4. **跨地圖送達是常態**：`target.send(...)` 走對方自己的連線，不看兩人在不在同一張圖。這是刻意的 ——
   「密語」的意義就是不在地旁邊也能說話；也因為如此，這條路徑不經 `FieldInstance.broadcast`。
5. **收到的密語用 `0x12` 送**（跟場地聊天同一個 sub-op）。這不是偷懶：`sub_472910` 的 `0x0A` 顯示文字時
   用的是**寄件者自己**保留的最後一段話（`CField + 28`），拿它送給收件者會顯示錯的內容（§4.31 的 ⚠️ 第 2 點）。
   代價是收件者的 client 分不出聊天與密語 —— 那是 2003 年 client 的形狀，不是我們的選擇。
6. **拒收（`0x1A` sub-op `0x22`）不實作**：形狀已知（`str name`），但 client 端沒有任何輸入會設定
   「我拒收密語」（那個開關的封包還沒找到）。沒有驅動者的 codec 是死碼，所以它留在 FINDINGS §6 第 17 項。
7. **氣球請求（`0x23` kind `0x22`）讀得出來、只記日誌**：那是 client 在聊天視窗關著時自己組的
   「請在我頭上畫氣球」請求；哪個 s2c 會畫氣球還沒定位，所以伺服器不對它做任何假設（也不回應）。
8. **密語不落地**：沒有離線訊息、沒有歷史紀錄，`--save` 的格式不動。要加的時候它是一個**新功能**
   （需要決定存在哪、留多久），不是這個封包的延伸。
9. **自己密自己**：client 自己會擋（`자신에게는 귓속말을 할 수 없습니다.`），所以伺服器不特判 ——
   真的收到就照一般路徑送達（收件者是自己），不多一條沒有證據可對的分支。

**被否決的選項與原因**：

- **建一個 `name → session` 索引**：與 ADR-018 的座位表重複，兩份狀態就可能不同步；線上人數不大時
  線性掃描的成本可以忽略。
- **離線也報「上次的地圖」**：訊息會說謊（client 會顯示「現在的位置是…」），而且存檔的 `mapId` 是
  「下次登入要進哪張圖」，語意不同。
- **大小寫敏感**：與 `nameTaken`（建立角色時的規則）不一致 —— 同一個名字在建立時不分大小寫，查找時分，
  只會讓玩家困惑。
- **把拒收做成 `GameEntryServer` 的 policy 選項**（像 `dropPolicy`／`--npc-walk` 那樣）：那會讓一個
  **沒有協定驅動者**的狀態看起來像規格；等開關的封包定位後再加，屆時只是多一個 codec 與一個分支。
- **密語也走 `FieldInstance.broadcast`**（先假設大家同圖）：跨圖是密語的定義，而且廣播會把別人的私訊
  送給同圖所有人。

**後果**：

- README 的「誰在線上」旁多一節「密語與找人」；`FINDINGS §6` 的第 4 項（`0x1A` 的 sub-op 表）打勾結案。
- 密語是**第一個用名字找人的路徑**：將來的好友名單、組隊邀請（`0x26` 的 party 家族）都會用到同一個
  `sessionNamed`，那時它會被移到 `net/online.ts` 還是留在這裡，等真的有第二個使用者再決定。
- 「誰看得到誰的名字」變成一個安全問題：任何人都能用 `0x23` 查任何線上角色的所在地圖。這是 2003 年的
  設計（`/헉추적` 之後變成正式指令），不是我們加的；要收緊（例如等級差、換圖頻率）是伺服器政策，
  屆時一個 `sessionNamed` 之外的鉤子就夠。

## ADR-020：復活＝伺服器換圖＋補滿 HP；「死亡」不進伺服器

**日期**：2026-10-16 ｜ **狀態**：已定案（請求與復活機制全部有證據；目的地與「不記死亡」是我們的選擇）

**背景**：ROADMAP 的「被怪物打不會掉血」把兩件事混在一起：**伺服器要不要算玩家的扣血**，以及
**玩家死了之後怎麼回來**。FINDINGS §4.32 把可以定位的都定位了：

- 死＝client 的動作位元組 `CUser + 180` ＝ 18／19（`sub_50B570`／`sub_464580`）；
- 2.2 秒後 client 自己彈出 `CUIRevive`（`CField + 680` 是那個計時器，寫入者仍未知）；
- 按 OK／Enter 送出 **c2s `0x0D` `kind = 0`**（`sub_4E9E70` → `sub_472590(0, nullptr)`）；
- **真正復活的是 `0x16`**：它重建場地與本機角色（`sub_4C2780` → `sub_51CBF0` → `sub_511030`），
  而同一包裡的 `CharacterData` 就是 client 畫 HP 條的那份紀錄（§4.21）。
- client **完全不讀** `returnMap`（執行檔裡沒有這個字串），所以「안전한 마을로（安全的村莊）」在哪是伺服器的答案。

**決策**：

1. **請求＝c2s `0x0D` `kind = 0`**，與傳送門（`kind = -1`）共用同一個封包與同一個 handler
   （`GameEntryServer.handleInteract`）；`name` 是空字串。三種 `kind` 都記在 `protocol/field.ts`。
2. **目的地＝`info/returnMap`**（`reviveMapId`，`game/map.ts`）：正整數且不是哨兵 `999999999` 就換圖，
   否則**重進當前這張圖**。哨兵一定要排除（它不是地圖 id，讀不到圖）；「重進當前圖」在村莊（
   哨兵的 25 張圖全都是村莊）與「`returnMap` 讀不到圖」兩種情況下都成立，而且是**真正的復活**而不是降級 ——
   `0x16` 重建本機角色才是活過來的機制。
3. **HP 在送 `0x16` 之前補成 `maxHp`，而且不再送 `0x0D` 差異包**。同一包已經帶了整份紀錄，送兩包就是
   兩份真相；`0x0D` 是「伺服器改了一格」的封包，而這裡伺服器改的是**整張圖**。
4. **伺服器不記「這個人死了」這個狀態**（**由 ADR-021 取代**：HP 的權威回到伺服器之後，「HP ＝ 0」
   就是那個狀態，`game/vitals.ts` 用它擋掉回復；仍然沒有一個獨立的死亡旗標）。client 只在真的死掉
   時送 `0x0D` `kind = 0`（由 HP 條與動作位元組自行判斷），伺服器不驗證那句話。
5. **伺服器不自己扣玩家的血、也不送 `hp = 0`**（**由 ADR-021 取代**：玩家 HP 現在由伺服器落帳，
   而 `hp = 0` 是 **client 自己回報的差值**套用後的結果，不是伺服器發明的數字；伺服器仍然不自己
   算傷害）。怪物打玩家的傷害是 client 用 `Mob/<id>.img/attack<i>` 自己算的（`sub_4885D0`），
   而 c2s `0x2C` 只有 mobId／旗標／動作／原點（§4.20.2）。
6. **`0x19`（放行閘門）照送**：`sub_472590` 送 `0x0D` 時會把 client 的互動閘門設起來，與點擊傳送門
   同一個閘門，所以復活也要放行，否則復活之後那個 client 就再也點不了東西。
7. **沒有死亡懲罰**（不掉經驗、不掉道具）：沒有任何證據，也沒有 client 的訊息；要加是政策，屆時是
   一個新 ADR。

**被否決的選項與原因**：

- **由伺服器主動送 `0x0D` `hp = 0` 來「殺」玩家**：不知道 client 收到 HP 0 之後會不會走 2.2 秒那條路
  （`CField + 680` 的寫入者未知），送出去等於賭一個沒讀過的機制。
- **復活時只留在原地送一條 HP 差異包**：死掉的動作位元組與屍體屬於**那張圖的本機角色**，不重建它
  就只是「HP 看起來滿了」而人還是死的。
- **把 `returnMap` 當成「最接近的村莊」自己算**（例如用座標或街道名猜）：資料裡有現成的答案，
  猜一個只會與原伺服器不同。
- **復活時順便補 MP**：沒有證據；死亡的機制是 HP，多改一格就是多一個要解釋的偏離。
- **加一個 `--revive-map <id>` 之類的覆寫選項**：目前資料說得很清楚（哨兵／指向村莊），多一個選項
  只會讓「這台伺服器行為不同」變成可能。

**後果**：

- `game/map.ts` 多了兩個 export（`RETURN_MAP_NONE`、`reviveMapId`），`net/loginserver.ts` 的
  `handlePortal` 拆成 `handleInteract`／`usePortal`／`revive`。`0x0D` 的三種語意集中在一個地方。
- 死亡的另一半（誰宣告、扣血）留在 FINDINGS §6 第 18 項；定位之後的接點是 `CField + 680` 的語意
  與 `0x2C` 的欄位（若真有傷害欄位藏在尾段）。屆時這一 ADR 的第 4、5 點要一起改寫。
- `analysis/map_meta.json` 的 `returnMap` 分布（25／65／8／2）成為資料面的驗收依據：新的地圖集
  （別的年分、別的區域）只要還有哨兵，`reviveMapId` 就還是對的。

## ADR-021：玩家 HP／MP 由 **client 回報差值**（c2s `0x1C`）、伺服器落帳並用 `0x0D` 回覆；伺服器不驗算傷害

**日期**：2026-10-17 ｜ **狀態**：已定案（**取代 ADR-020 第 4、5 點**；那個 ADR 說這兩點會在
「死亡的另一半」定位後改寫，這就是改寫）

**背景**：ROADMAP 的「被怪物打不會掉血」缺的是「誰扣玩家的血」。答案是：**client 自己**，
而且扣血不經過任何伺服器封包 ——

- 怪物 AI 在 client（`sub_4862C0` → `sub_487D10` → `sub_4885D0`，§4.20）；
- 本機玩家被打那條：`sub_511C60` 每幀找重疊的怪物 → `sub_4C8ED0` 算傷害 → `sub_5114A0` 播受擊動作；
- 這一整條路**都不寫玩家紀錄的 HP**：紀錄的 `+53`／`+55` 只有 s2c `0x0D`（`sub_45E0D0`）、
  `CharacterData` 進場（`sub_45D840`）、道具效果（`sub_4BDDC0`／`sub_518BF0`）與一個**沒有呼叫點**的
  升級 routine（`sub_4C71C0`）會寫；
- 所以 `sub_5114A0` 唯一能做的是**回報差值**：`sub_55B870(-damage, 0, 0)`，也就是 c2s
  `0x1C` = `[0x1C][u32 flags][s16 hpΔ][s16 mpΔ][u8 flag]`（§4.33，`objdump` 逐 byte）；
- 地圖自己的回復走同一個封包（`sub_558950`：HP ＋10、MP ＋3，每 10000 ms，旗標 byte 可能是 1）。

**決策**：

1. **接受並落帳**：`GameEntryServer.handleStatReport` 讀 `0x1C`，交給 `game/vitals.ts` 的
   `applyVitalReport` 就地套用在角色的紀錄上（那是 `0x16` 送出、存檔寫下的同一份物件）。
   差值而非絕對值，所以不需要信任任何「現在的 HP 是多少」的宣稱。
2. **回覆 `0x0D`**：只送**真的動了的欄位**（`applyVitalReport` 回傳的 `StatDiff`）。這是玩家看得到
   血條下降的唯一機制（紀錄的 HP 只有 `0x0D` 會寫），所以「接受但沉默」等於這個功能不存在。
3. **夾在 `[0, max]`**，並**在 HP ＝ 0 時不接受正向 HP 差值**。client 的回復不擋死亡（`sub_558950`
   只擋滿血），沒有這條規則屍體會每 10 秒站起來 10 點；補滿 HP 是復活那條路（ADR-020）。
   MP 不受這條規則影響。
4. **伺服器不驗算傷害**。`0x2C` 裡沒有傷害欄位（§4.20.2），公式住在 `Mob/<id>.img/attack<i>` 與
   client 的 `sub_4C8ED0`；原 2003 server 也是照單全收。要驗算＝把怪物 AI 搬到伺服器上，那是
   一個新的決策，不是這一則的一部分。
5. **不為遠端玩家的 HP 發明封包**。s2c `0x1C`（別人進場）沒有 HP 欄位；別人的血條在他自己的 client
   上是自己算的。這一格維持原樣。

**被否決的選項與原因**：

- **伺服器自己算傷害（用 `Mob/<id>.img` 的 `attack<i>`）**：等於在伺服器重寫一份怪物 AI 與命中判定，
  而 client 才是原設計裡的那一份；做出來的兩份會不一致（同一隻怪在 client 與伺服器上打不同的數字）。
  留為後續選項（例如以後要做防作弊）。
- **把 client 回報的傷害當成「絕對 HP」來存**：差值就是差值；存絕對值會讓一次遺漏的回報永久偏移。
- **只記帳、不回 `0x0D`**：這樣 client 的血條永遠不會動（紀錄的 HP 只有 `0x0D` 寫），功能等於沒做。
- **死亡時由伺服器主動送 `hp = 0`／主動送 `0x16`**：`hp = 0` 現在是回報的結果，不是伺服器發明的；
  而復活是玩家的選擇（`CUIRevive` 的 OK），不是伺服器替他決定。
- **順便修「別人的血條」**：沒有任何 s2c 封包帶遠端 HP（只有自己那份 `0x0D`），要加就得先發明格式 ——
  維持 2003 年的樣子。

**後果**：

- `protocol/field.ts` 多一個 c2s opcode（`statReport = 0x1c`）與三件套 codec，旗標與 `0x0D` 共用
  `statDiffFlag`（兩份封包的 bit 只有一處定義）；`schema.ts` 目錄多一列（60 列）。
- `game/vitals.ts` 是新的「玩家 HP／MP 的伺服器規則」模組；`loginserver.ts` 的 dispatch 多一個
  分支與 `handleStatReport`。
- **HP 的權威在伺服器上，但數字的來源是 client**：這是一個刻意的取捨（原設計如此）。任何未來的
  防作弊／傷害驗算都必須先重寫怪物 AI，並且會與 client 的本地計算產生分歧 —— 屆時要一則新的 ADR。
- 死亡那一格 ROADMAP 可以從 🟡 收斂：`hp = 0` 由伺服器算出來、client 自己走 2.2 秒與 `CUIRevive`
  （§4.32）。剩下的只有 `CField + 680` 的寫入者（純學術：不影響這條鏈）。

## ADR-022：用掉道具＝**讀 client 自己的 `spec`**；拒絕也要回一個空的 `0x0B`；buff 道具一律拒絕

**日期**：2026-10-17 ｜ **狀態**：已定案（ADR-010 的商店決策的下一半：買到的東西怎麼用）

**背景**：§4.34 把 use 這條路定位完了：

- c2s `0x18`／`0x19` 都只有 `[s16 slot][u32 itemId]`（`0x18` 由道具欄與快捷鍵送、`0x19` 只有道具欄送，
  家族由 `itemId/10000` 決定：`200/201/202` → `0x18`、`203` → `0x19`；`0204`／`0207` 兩邊都不是）。
- 道具做什麼**不在封包裡**：那是 `Item/Consume/0XXX.img/<id>/spec`（§4.34.3 有全表）——
  `hp`／`mp` 是定值，`hpR`／`mpR` 是上限的百分比，`0203` 的 `moveTo` 是地圖 id（`−1` ＝最近的城市）。
- client 自己的閘門（`*(this+6) == 0`、本機 HP > 0、200 ms／500 ms 節流）只決定「送不送得出去」；
  **道具真的被消耗、血真的回、圖真的換，都要靠伺服器的回包**（紀錄的 HP 只有 `0x0D` 會寫，
  道具欄只有 `0x0B` 會改，場地只有 `0x16` 會換）。
- 效果表在 client 裡（`sub_518BF0` → `sub_4BDDC0` 寫紀錄的 HP／MP XOR 對），但**把 `spec` 讀成那張表的
  loader 沒有定位**，而且那些欄位名在 `.exe` 裡沒有任何字面字串（§4.34.4）。

**決策**：

1. **效果一律讀 `spec`（WZ），不移植那張表**：`game/items.ts` 的 `consumeSpecOf(archive, itemId)` 直接讀
   `Item/Consume/0XXX.img/<id>/spec`。理由與價格一樣（ADR-010）：檔案就是 client 的那一份資料，
   兩邊同源就不會分歧；而唯一能證明原 client 怎麼算的 loader 還沒找到，抄一張沒定位的表等於猜。
2. **每一個使用請求都必須有回包**：允許 → `0x0B`（`put` 剩下的數量／`clear`）＋ 藥水的 `0x0D` 或
   卷軸的 `0x16`；**拒絕 → 空的 `0x0B`**（`result` 非 0）。理由：client 的閘門由回包解開
   （`sub_463050` 在 `sub_55BAB0` 裡先被呼叫，§4.34.2），沉默會讓玩家連下一罐都喝不了；
   而「空的 `0x0B`」在語意上正好是「什麼都沒變」。
3. **先驗再扣**：`spec` 查不到／會動的欄位一個都沒有／滿血／欄位裡不是它宣稱的道具／`0x19` 的目的地
   讀不到圖 → 全部在 `takeItem` **之前**拒絕。滿血喝藥水不該浪費一罐，卷軸不該消失在一個不存在的圖。
4. **buff 道具（`spec/time` 家族）拒絕而不是半套用**：伺服器沒有 buff 狀態，也還沒解出哪個 s2c 會讓
   client 畫圖示（`0x0D` 的 `panelFlags != 0` 區塊，§4.21.6）。`ConsumeSpec.unapplied` 記下未定位的欄位，
   非空就拒絕 —— 道具留在袋子裡，等那個功能真的做出來再用（§6 第 20 項）。
5. **`hpR`／`mpR` 取整是伺服器的選擇**：百分比乘上限後**向下取整**（半點 HP 不是血條畫得出來的東西）。
   原 client 的取整方式未定位（§6 第 19 項），這是文件上明講的選擇，不是證據。
6. **`moveTo = −1` 用「最近的城市」＝地圖的 `info/returnMap`**（`reviveMapId`）：復活（ADR-020）已經回答
   過同一個問題，兩個地方用同一份答案；村莊的哨兵 `999999999` 就是「重進這一張」。
7. **新角色的起始錢是一個明講的伺服器選擇**：`--start-mesos <n>`（預設 **0** ＝ 2003 年新角色的樣子）。
   沒有它就買不了任何東西（而掉落是機率），所以測試與實跑要用它；它只影響**之後建立**的角色。
8. **三間店，每一間都賣 마을 귀환 주문서**（ADR-010 的商店表的延伸）：`1010100` 리나、
   `2003` 로빈、`12100` 마이（암허스트，新角色／復活都會到的那個村），마이 多一個 헤네시스 귀환
   주문서（`02030004`，`moveTo = 100000000`）—— 指名一張圖的卷軸讓「用道具換圖」在測試裡可觀察。

**被否決的選項與原因**：

- **在伺服器上抄一個「效果表」（例如把 `hp` 轉成固定數字、`hpR` 當 50＝固定值）**：那就是第二份資料，
  而且會與 client 的 `spec` 分歧（엘릭서 在 100 級與 20 級喝的效果不同）。
- **拒絕時沉默**（或只回 `0x0D`）：client 的閘門等 `0x0B`，沉默＝玩家卡在「用不了東西」的狀態。
- **拒絕時回一個「假的成功」**（消耗道具但不做事，或回 `0x0B` 說欄位變了）：那是在騙 client 的 UI，
  而且與存檔不一致（存檔是伺服器寫的）。
- **先扣道具再驗**：滿血喝藥水就浪費一罐、卷軸換圖失敗就消失 —— 兩者都是玩家看得到的損失。
- **buff 道具「先套一半」**（忽略 `time`／只送 `0x0D` 的能力值）：客戶端會顯示一個沒有時間的加成，
  而伺服器沒有那個狀態 → 兩邊立刻分歧。
- **`moveTo` 用 `fieldLimit`／`town` 之類的旗標判斷「哪張圖是村莊」**：那些欄位在這個 client 裡連
  字串都沒有（§4.32 的註記），而 `info/returnMap` 已經有答案。
- **讓新角色預設帶錢**（例如 1000 mesos）：2003 年的新角色身上是 0；要給錢是那個伺服器的選擇，
  所以做成**旗標**（`--start-mesos`）而不是預設值。

**後果**：

- `protocol/field.ts` 多兩個 c2s opcode 與三件套 codec；`schema.ts` 目錄多兩列（**62** 列：
  39 byte-exact／19 partial／4 skeleton）。
- `game/items.ts` 是新的模組（`spec` 的讀取與換算）；`net/loginserver.ts` 多 `handleUseItem`／
  `useMapItem` 與一條 dispatch 分支；`cli.ts` 多 `--start-mesos`；`game/shops.ts` 的 `SHOPS` 變成三間店。
- 測試 +9（`items.test.ts` 6、`field.test.ts` 1、`serve.test.ts` 1＋商店列、`shops.test.ts` 1）→
  **384**；`whisper_probe.mjs` 多 8 項 → 共 **31** 項檢查。
- 剩下的兩個小缺口都在 §6（loader 與 buff 家族），都不擋「買 → 喝 → 換圖」這條鏈。

## ADR-023：表情是**別人的畫面**的事 —— 廣播 `0x27`、不回送給送出的人、沒有回包義務

**日期**：2026-10-17 ｜ **狀態**：已定案（§4.35；延伸 §4.24 的「哪些封包是場地的事實」）

**背景**：§4.35 把 `CUserPool` 的 `0x27` 讀完，並接回它的來源：

- **c2s `0x13`** 是唯一送出者 `sub_511E20` 的 case 10，也就是**按鍵分派器**裡的「F1–F7」：封包本體是
  一個 `u32`（`CUser + 172`），而且 **client 在組封包之前就把那張臉套在自己身上了**
  （`.text:00511FD8` 的 `sub_509790` 早於 `00511FDF` 的 `push $0x13`）。
- **九張臉**是 `.data:0x5B20D8` 的九個 `wchar_t*`：`blink`／`hit`／`smile`／`troubled`／`cry`／`angry`／
  `bewildered`／`stunned`／`vomit`；索引 1（`hit`）由 client 在被打時自己使用
  （`sub_5114A0`：`sub_509790(this, 1, 1500)`）。
- **s2c `0x27`** 是同一張臉放在別人身上：`u32 characterId` ＋ `u32 emotion` → `sub_509790(user, …)`；
  池裡沒有的 id 會讓整包被丟掉（所以對不在場的角色送它是安全的）。

**決策**：

1. **只廣播，不回送給送出的人**：`0x27` 送給同場地的其他人（`FieldInstance.broadcast(…, characterId)`）。
   理由和 `0x22`（自己的移動路徑）、`0x29`（自己的升級特效，ADR-015）一樣：client 已經自己套用過了，
   回送只會把同一個值再設一次。
2. **不為「被打的 `hit`」送任何封包**：每個 client 都在本機自己算怪物傷害（§4.33），別人的受擊表情
   也是每個 client 自己算出來的。伺服器沒有這個事件的來源，也不去發明一個。
3. **沒有回包義務，不合法就丟**：表情不像點擊（`0x33`）或使用道具（`0x18`／`0x19`），client 沒有
   在途請求閘門，所以 `> 8` 的索引由 codec 直接拒絕、handler 記一行日誌後丟掉，不回空包。
   （範圍是 client 自己的：`sub_509790` 測 `n8 <= 8`，畫圖端把 `> 8` 夾成 0。）
4. **不記狀態**：臉是「現在的樣子」，不進存檔、換圖不重送（新進場的人從 `0x1C` 的紀錄開始畫）。
   伺服器不需要一份「誰現在什麼表情」的表 —— 那會是第二份真相，而且沒有任何封包讀它。
5. **名稱用 client 自己的九個節點名**（`EMOTION_NAMES`），不編譯成韓文：`Data.wz` 與 `.exe` 裡都沒有
   韓文對應（按鍵設定不在資料檔裡），編一個名字就是把猜測寫進程式。

**被否決的選項與原因**：

- **把表情回送給送出的人**：多一個封包、多一次 `SetFace`，而且兩邊都「先自己套用再送」的設計會被
  掩蓋成「其實要等伺服器」。
- **伺服器記住每個人的表情並在進場時重送**：client 的表情由它自己的動作狀態決定，新進場的人畫的是
  `blink`；要重送就得先有一份狀態，而那份狀態沒有任何證據支持它是原設計的一部分。
- **把不合法的索引夾成 0 再廣播**：那等於替 client 修封包。client 自己送不出這種值
  （`n8 <= 8` 兩處都擋著），會送出來的是別的實作 —— 丟掉並記日誌比替它猜更誠實。
- **在這個 slice 順便實作氣球（s2c `0x1F`）**：形狀已定位（`[u32 characterId][string text]`、
  5 秒、`"%s : %s"`，§4.35.5），但它的驅動者（c2s `0x23` kind `0x22`）第二個字串來源未定位 ——
  送錯字串等於在畫面上顯示錯的東西，所以留在 §6 第 17 項(b)，不進這一刀。

**後果**：

- `protocol/field.ts`：`CLIENT_FIELD_OPCODE.emotion = 0x13`、`FIELD_OPCODE.userEmotion = 0x27`、
  `EMOTION_NAMES`／`EMOTION_NEUTRAL`／`EMOTION_HIT`／`EMOTION_MAX`／`emotionName` 與兩組 codec；
  `schema.ts` 多兩列（**64** 列：41 byte-exact／19 partial／4 skeleton）。
- `net/loginserver.ts` 多一條 dispatch 分支與 `handleEmotion`；`world.ts` 不動（用既有的
  `broadcast(packet, exceptCharacterId)`）。
- 測試 +2（`field.test.ts` 的表格與兩個方向的黃金 bytes、`serve.test.ts` 的兩個真 socket
  「別人收到 `0x27`、送出的人什麼都沒收到、`9` 被丟掉」）→ **386**；`whisper_probe.mjs` 多 3 項 → **34**。
- 這一格收掉 `CUserPool` 的 `0x27`；同一個範圍剩下的是 `0x1E`／`0x20`／`0x21`／`0x23`–`0x26`／`0x28`／
  `0x2A`（其中 `0x1F` 的形狀已定位）。

## ADR-024：起始外觀 —— `appearanceA`／`appearanceB` 是臉與頭髮，缺的一律補起始值

**背景**：`0x1C`（別人進場）的第一個 u32 一直當成「外觀版本鍵」送 0，`createCharacter` 也從不寫紀錄的
`appearanceA`／`appearanceB`（`0x06` 的十個 u32 只進日誌）。結果是**每個角色都沒有臉、沒有頭髮** ——
「建立的角色全身空著」（§6 第 16 項）講的就是這件事。

**證據**（全部是呼叫鏈，見 FINDINGS §4.8.1a／§4.11.3c）：

- `0x1C` 的第一個 u32 → `sub_507A20` → `sub_508260` → `CUser+68`，而 `+68` 正是表情／動畫播放器
  `sub_509070` 拿給 `sub_408400` 去 `Character/Face/*.img` 找情緒節點的那個**臉**（`sub_45D500` 讀
  `"0"`..`"8"`）。第二個 u32 的孿生路徑是 `0x28` 的 flag bit 0（`sub_5221A0`：`this[17] = u32`）。
- 紀錄的兩個字：`sub_42E2C0` 把 `+18`（`appearanceA`）餵 `sub_424590`（與 `sub_508260` 同形，寫的是
  同一格臉），把 `+22`（`appearanceB`）放進外觀第 0 格 —— 第 0 格是 `sub_45F340` 給 `3xxxx`
  （`Character/Hair`）的那一格（§4.11.3b）。
- `0x06` 的十個 u32：`sub_431620(1002)` 依 `CUINewChar + 496 + 8k` 的順序送六個下拉選單
  （`.c:57462`），而預覽刷新 `sub_430D00` 顯示這六格是臉／`src[0]`／`src[5]`／`src[6]`／`src[7]`／`src[11]`
  —— 臉、頭髮、上衣、褲子、鞋子、武器；尾巴四個是骰子（`+420..+432`，`sub_430630`）。

**決策**：

1. **正名**：`0x1C` 的第一個 u32 由 `avatarKey` 改成 `face`（`UserEnterField`、`schema.ts` 同步），
   `FieldMember` 多一個 `face`。留著錯的名字等於留著一個會被下一個人照著實作的誤解。
2. **紀錄的 `appearanceA`／`appearanceB` 就是臉與頭髮**：`createCharacter` 用 `0x06` 的前兩個 u32 寫入；
   `appearanceB` 同時進 `0x1C` 的外觀清單（`avatarItemsOf` 把頭髮放在最前面）—— `sub_45F340` 靠 id 前綴
   歸位，清單唯一的規則是「不得含 0」。
3. **缺外觀的角色補起始值，而且只在送出的邊界補**：`lookOf`（臉 `20000`、頭髮 `30000`，即
   `Data.wz` 裡的 `Character/Face/00020000.img` 與 `Character/Hair/00030000.img`）＋`withDefaultLook`
   （`0x16`、`0x02`／`0x05` 的回包）。**存檔不因此改寫**：0 仍然讀作「還沒設定」。
4. **衣服與骰子那八個 u32 繼續只記日誌**：衣服變成穿戴裝備前必須先證明「穿戴格欄號 ↔ 部位格」是同一套
   號碼；骰子哪一顆是哪個能力值沒有文字證據（`.exe` 裡沒有那四個韓文字串）。寧可少給，不要發明。
   （**衣服那一半已由 ADR-025 取代**：格號的證據鏈在 §4.11.3d；骰子仍然只記日誌。）

**被否決的選項與原因**：

- **繼續把第一個 u32 當「版本鍵」送 0**：client 會拿 0 去畫一個不存在的臉部部位（`Character/Face/00000000.img`），
  等於明知有問題還送；而且第二條證據（`sub_42E2C0`）也指向同一格。
- **把 `chardata.ts` 的 `hair`（`u32 @+27`）當成頭髮**：`sub_45D840` 只是把它原封不動存下來，紀錄路徑
  沒有任何人讀它，而畫面上真正的頭髮來自 `+22`。改名會動到存檔欄位卻沒有任何行為差異 → 只改註解。
- **在 `characterDataOf`（codec）裡補起始值**：那會讓每個 golden 測試的 bytes 跟「伺服器政策」綁死；
  補在送出邊界語意清楚，也留得住「原樣」。
- **一律蓋掉 client 選的臉／頭髮**：那會讓「選了沒生效」變成長期行為，而 `0x06` 的前兩個 u32 現在有證據。

**後果**：

- `protocol/chardata.ts`：`DEFAULT_FACE_ID`／`DEFAULT_HAIR_ID`／`lookOf`／`withDefaultLook` 與三個欄位的
  註解；`protocol/field.ts`：`avatarKey` → `face`；`net/loginserver.ts`：`createCharacter` 用 `0x06` 的前兩個
  u32、`avatarItemsOf` 帶頭髮、`setFieldOf`／`0x02`／`0x05` 補起始值；`game/world.ts`：`FieldMember.face`。
- 測試 +4（新的 `test/look.test.ts`）＋既有案例改成帶臉與頭髮 → **390**；`whisper_probe.mjs` +2
  （「別人的 `0x1C` 帶著他自己的臉與頭髮」）→ **36 項**。
- `schema.ts` 的 `0x1C` 列改名並補上兩個「讀了就丟」的 u32（**64** 列不變）。
- 剩下的兩塊留在 §6 第 16 項：(a) 骰子的能力值對應、(b) 衣服 → 穿戴裝備。

## ADR-025：起始裝備 —— `0x06` 的第 3–6 個 u32 直接變成**穿戴裝備**，格號由 itemId 的 part code 決定

**日期**：2026-10-17 ｜ **狀態**：已定案（§4.8.1a／§4.11.3d；取代 ADR-024 決策 4 的衣服那一半）

**背景**：ADR-024 把臉與頭髮接上之後，`0x06` 剩下的第 3–6 個 u32（上衣、褲子、鞋子、武器）仍然只進
日誌，於是每個新角色都穿著內衣上線 —— `0x1C` 的清單是「頭髮 ＋ 穿戴中的裝備」，而穿戴群組一直是空的。
擋住的是「`CharacterData` 穿戴格的欄號 ↔ 部位格」這一層：以前只有 `sub_42E2C0` 的一條線性迴圈當線索。

**證據**（四條互相獨立的呼叫鏈，§4.11.3d 有出處行號）：

1. `sub_45F340` 是**唯一**讀 part code（`itemId / 10000`）的函式，它把 id 寫進 15 格外觀陣列的哪一格
   就是上表（`100`→1 … `104`／`105`→5、`106`→6、`107`→7、`110`→9、`109`→10、`13xxxxx`／`14xxxxx`→11、
   `3xxxx`→0）。`0x1C` 的清單餵的就是它。
2. `sub_45F610`（`CharacterData::Encode`）寫穿戴群組時的格號是**陣列索引 1..14**（`n14 = 1; … while
   (n14 <= 14)`），`sub_45FCC0`（`Decode`）反向寫回 `this + 8 * 格號 + 122`：兩支逐格對應。
3. `sub_42E2C0`（char-select 的 avatar）解完紀錄後用一個線性迴圈 `srca[1 + k] = worn[k].itemId`
   （k = 1..14），`srca[0]` ＝ 紀錄的頭髮 —— **穿戴格 k ↔ 外觀格 k**。
4. `sub_430D00`（建立角色對話框的預覽）把六個下拉選單寫進外觀格 0／5／6／7／11，而那六個 u32 就是
   `0x06` 的送出順序。

⇒ 三條路（part code 表、穿戴群組的編碼／解碼、紀錄→avatar 的線性迴圈）指向同一組號碼，而第 4 條
把它接回 `0x06` 的字序：上衣 5、褲子 6、鞋子 7、武器 11。

**決策**：

1. **第 3–6 個 u32 一律變成穿戴裝備**：`wornOfLook`（`protocol/chardata.ts`）把每個 id 放到
   `wornSlotOfItem(id)` 那一格（＝ part code 決定的外觀格），`createCharacter` 用 `withWorn` 併進
   新角色的穿戴群組。**不是**「第幾個字就放第幾格」：字序與格號是兩件事，`104xxxx`／`105xxxx` 這兩個
   字都進第 5 格。
2. **放不進去的 id 直接略過**（`0`、臉、頭髮、消耗品、`111xxxx`）：client 自己對沒有 part code 的 id
   也不會寫任何一格（`sub_45F340` 的 `default` 就是 break），所以略過等於照抄。
3. **道具紀錄用 `equipSlot(itemId)`，`ruc` 0**：WZ `info`（`+44` 的升級次數、`+46..+74` 的 15 個能力）
   這個伺服器還沒讀，先送 0 而不是猜一個。畫得出來與否只看 id（client 拿 id 去 `Character/Clothes/…`），
   所以 0 只影響工具提示裡的「업그레이드 가능 횟수」。
4. **骰子（第 7–10 個）仍然不落地**：新角色的能力值維持伺服器自己的 5／50。`sub_430690` 只用 `%d`
   把它們畫成四行（y = 293／313／333／353，`.c:56546`），沒有任何字串能證明誰是 STR／DEX／INT／LUK。
5. **只在建立角色時做，不改寫既有存檔**：舊存檔的角色繼續是「沒有穿戴裝備」（＝內衣），要換外觀得走
   之後真的解出來的換裝路徑；伺服器不會替既有角色補一套自己發明的衣服。

**被否決的選項與原因**：

- **按 `0x06` 的**字序**放格號**（上衣放第 3 格…）：`sub_45F340` 的表就是「id 前綴決定格號」，
  字序只是對話框控制項的順序。照字序放會讓 client 把褲子畫到臉上（`srca[3]` 是眼睛裝飾那一格）。
- **伺服器自己配一套起始裝備**（像臉 `20000`／頭髮 `30000` 那樣）：臉與頭髮有「0 等於沒有這個部位、
  整顆頭會空掉」的硬理由，衣服沒有 —— 0 就是「沒穿」，client 畫得出來。憑空送一套等於替玩家做選擇，
  而且會蓋掉 `0x06` 真正的值。
- **把衣服塞進 `appearanceB` 或外觀清單以外的欄位**：`0x1C` 的清單（`sub_45F340` → 15 格）與穿戴群組
  （`sub_42E2C0` → 同 15 格）是兩個入口指向同一組格號，塞去別的地方只會有一半的畫面正確。
- **先做 WZ `info` 的 `ruc` 再落地衣服**：`ruc` 是可見性為零的細節（工具提示），不該擋住「角色穿得
  出來」這件事；反過來先落地才看得到 `0x05`／`0x1C` 的真實位元組。

**後果**：

- `protocol/chardata.ts`：`AVATAR_SLOT`、`avatarSlotOfItem`、`wornSlotOfItem`、`LOOK_WORD`／`LOOK_WORDS`、
  `wornOfLook`、`withWorn`；`net/loginserver.ts`：`createCharacter` 併穿戴群組、`describeLookWords`／
  `describeWorn` 兩個日誌（骰子仍然看得見）。
- 出口自動跟著：`0x05`／`0x02` 的回包（`characterDataOf` 看到 `worn` 非空就補 `flags & 0x02`）與 `0x1C` 的
  `avatarItems`（`avatarItemsOf` 讀同一個 Map）。
- 測試 **+8**（新的 `test/worn.test.ts`）＋ `serve.test.ts` 的建立流程與同場地 `0x1C` 各多一組斷言 →
  **398**；`whisper_probe.mjs` +3（兩次建立各驗一次穿戴格，加上「每個穿戴 id 都出現在別人的 `0x1C`」）
  → **39 項**。
- §6 第 16 項只剩 (a) 骰子；FINDINGS 新增 §4.11.3d（格號表＋四條證據）。

## ADR-026：轉播別人的揮擊用 s2c `0x23` —— 只給其他人、只放收下的怪、沒有來源的欄位送中性值

**決策**：玩家送出 c2s `0x0F`（普攻）時，伺服器除了把傷害記在怪物身上，還把這一刀轉播給**同場地的其他人**：
s2c `0x23`（`encodeUserAttack`，FINDINGS **§4.11.7b**）。三個細節是決策的一部分：

1. **不送給攻擊者自己**。`sub_512F90` 在寫封包**之前**就跑過同一組特效函式（`sub_50DAA0`／`sub_50D7F0`／
   `sub_4882F0`，`.c:279017`–`279042`），他的畫面已經有這一刀了；規則與 `0x27`／`0x29` 相同（ADR-023）。
2. **只放這場地真的收下的怪**（`applyDamage` 有回傳的目標）。觀察者的畫面要與世界的事實一致；打到這場地沒有的怪，
   只會讓別人看到不存在的傷害數字（那個目標本來就只是 client 的宣稱）。
3. **沒有來源的欄位送中性值，不猜**：`skillLevel`／`skillId` ＝ 0（普攻沒有技能節點）、`afterimage` ＝ 0
   （每張 `Character/Afterimage/*.img` 都有 `0` 這個子節點）、第 7 個 `u32` ＝ 0（只有 `0x24` 的 handler 會收）；
   `speed` 直接**照抄**攻擊者封包裡的 byte 4。

**理由**：2003 年的 client 就是這樣畫「別人打怪」的 —— 收端跑的是攻擊者自己也跑的那組函式（§4.13.1／§4.11.7b），
所以轉播裡每個欄位都是攻擊者已經算過的東西；伺服器只負責挑收件人與挑目標。

**被否決的選項與原因**：

- **連攻擊者也送一份**：他的 client 早就在送包前播過同一刀（見決策 1 的出處），再送一次等於要 client 自己擋重播。
- **只轉播命中、不轉播落空**：落空的揮擊在別人畫面上也是揮擊（client 的送包端不區分），所以 `targetCount = 0`
  的 `0x23` 照送，只是沒有目標記錄。
- **伺服器自己算 `afterimage`／`speed`**：兩者都是「武器資料 ＋ client 端邏輯」（`sub_4BE270`／`sub_4BE8B0`）的產物；
  `speed` 有現成來源（封包自己的 byte 4），`afterimage` 沒有，所以只有後者送 0。
- **把魔法／技能（`0x10`／`0x11`）一起轉播**：那要走 s2c `0x24`／`0x25`，而兩支套用函式只讀到結構
  （`0x24` 多收那個 `u32`、兩支都用子彈型特效那一組），欄位對應不明之前不實作。
- **把第 4 個 byte 繼續叫 `targetCap`**：收端把它交給 `sub_508690` → `sub_508700`（`(n+5)/8` 乘進每格延遲、
  夾 0..6），只有「速度」說得通（§4.13.1c）；名字留著會讓下一個讀 code 的人以為它管目標數。

**後果**：

- `protocol/field.ts`：`FIELD_OPCODE.userAttack`（0x23）＋ 當時叫 `userMagicAttack`／`userSkillAttack` 的 `0x24`／`0x25`
  （**ADR-027 改名為 `userShootAttack`／`userMagicAttack`**）、
  `UserAttack`／`readUserAttack`／`encodeUserAttack`／`describeUserAttack`（**拒絕 `mobId 0` 的目標記錄** ——
  讀端會把它當空位而少讀尾巴）；`ClientAttack.targetCap` → `speed`（含 schema 與測試）。
- `net/loginserver.ts`：`applyAttack` 改成「先收集、後送」（揮擊 → 怪物反應 → 獎勵），新增 `relaySwing`。
- 測試 **+3 → 401**；`whisper_probe.mjs` **+8 → 47** 個檢查；`schema` 目錄 **65 個封包**
  （41 byte-exact／20 partial／4 skeleton）。
- 未實作：`afterimage` 的正確子節點（`sub_4BE270` 未定位）、`speed` 的抖動來源（`sub_4BE8B0` 第三個參數）。
  （本 ADR 決策 3 裡「第 7 個 `u32` ＝ 0」與被否決的「把 `0x10`／`0x11` 一起轉播」兩點，**由 ADR-027 取代**。）

## ADR-027：射擊（`0x10`）與魔法（`0x11`）也轉播，用的 opcode 由**渲染器**決定 —— 一對一是 `0x23`↔`0x0F`／`0x24`↔`0x10`／`0x25`↔`0x11`

**日期**：2026-10-17 ｜ **狀態**：已定案（取代 ADR-026 的兩點：第 7 個 `u32` 送 0、以及「`0x10`／`0x11` 暫不轉播」；
`0x23` 那一半照舊）。證據在 FINDINGS **§4.11.7c**。

**決策**：

1. **三支 c2s 攻擊各有自己的 s2c 孿生兄弟，表寫在 `ATTACK_RELAY_OPCODE`**：`0x0F`→`0x23`、`0x10`→`0x24`、`0x11`→`0x25`。
   不在表上的 opcode 不轉播（不猜渲染器）。
2. **判準是渲染器，不是「是不是技能」**：三個 sender 與三個套用函式的呼叫集合比對下來，`sub_41B630`（子彈型特效）
   只在 c2s `0x10` 與 s2c `0x24`、`sub_41B850`（魔法特效）只在 c2s `0x11` 與 s2c `0x25`，而 `0x0F` 與 `0x23` 的
   呼叫集合完全相同。⇒ opcode 選的是「觀察者要用哪一支特效」。
3. **兩個 opcode 的名字一起更正**（FINDINGS §4.11.7c 的證據）：`0x10` 是**射擊**——sender 只服務弓／弩／爪
   （`sub_4657F0(武器 id) ∈ {45,46,47}`），而且挑的是箭／弩箭／飛鏢；`0x11` 才是**魔法**——唯一上游是法師技能
   `2001005`／`2101005`（`sub_518BF0` 的 `LABEL_53 → sub_5195D0`，而 `sub_5195D0` 只是 `sub_514D30` 的別名）。
   `CLIENT_FIELD_OPCODE.magicAttack`（`0x10`）→ `shootAttack`、`skillAttack`（`0x11`）→ `magicAttack`；
   `FIELD_OPCODE.userMagicAttack`（`0x24`）→ `userShootAttack`、`userSkillAttack`（`0x25`）→ `userMagicAttack`。
4. **`0x24` 的第 7 格（`u32`）＝投射物的 item id，而且要用「格號 → id」查一次**：c2s `0x10` 帶的是
   **USE 分頁的格號**（`sub_511630` 的回傳值；item id 走 out-param `Args`），`0x24` 的收端要的是 id
   （`bottom / 10000 == 207` 才把飛鏢家族的每一排往下挪 120 px，並當 `sub_41B630` 的最後一個參數）。
   伺服器因此用**自己對那個分頁格的紀錄**（`projectileItemOf`）回答；**查不到就送 0**——原伺服器有那本帳，
   我們沒有那筆資料時送中性值，而不是把格號當 id 送出去。`0x23`／`0x25` 的 handler 不收這一格，一樣送 0。

**理由**：轉播的價值就是「別人看到你在打」；只轉播揮擊會讓弓手／法師在同場地變成**看不見的傷害來源**
（怪物會閃、會死，但沒有攻擊動作）。一對一既然是渲染器的硬事實，轉播只要照抄攻擊者已經算過的東西
（動作、`speed`、目標、傷害與受擊動畫），再補上唯一缺的那一格（投射物 id）。

**被否決的選項與原因**：

- **一律用 `0x23`**：觀察者的 client 會跑 `sub_520F20`（揮擊那組），弓／法師的攻擊會被畫成近戰揮刀，
  而且 `sub_5095A0` 拿到的動作 id 在弓的動作表裡可能不存在——`sub_508690` 是閘門，結果是整包安靜地不播。
- **把 `0x10` 的格號原封不動寫進第 7 格**：格號（1..96）永遠不會 `== 207xxxx`，等於送 0，但會讓
  「這一格是 item id」這個已證的語意變成謊話。
- **伺服器自己從 WZ 推導 `afterimage`**：`sub_4BE270`（選子節點的那支）還沒定位，維持 ADR-026 的決定：送 `0`
  （每張 `Character/Afterimage/*.img` 都有子節點 `0`）。
- **幫 `0x24`／`0x25` 補 `skillLevel`／`skillId`**：c2s 的兩個 opcode 都沒有這兩格，我們也沒有技能系統；
  送 0 ＝「沒有技能節點」，收端的 `sub_521400`／`sub_521AD0` 對 `right == nullptr` 是有防護的。

**後果**：

- `protocol/field.ts`：`ATTACK_RELAY_OPCODE`、`USER_ATTACK_OPCODES`、`encodeUserAttack(attack, opcode)`、
  `ClientAttack.projectileSlot`（原 `unknownU16`）、`UserAttack.projectileItemId`（原 `unknownU32`；**「是 item id」這一半是推論**，
  硬證據只有收端的用法與 `207` 那個判斷，見 §4.11.7c 最後一點）。
- `net/loginserver.ts`：`relaySwing` → `relayAttack`（查表、查投射物 id、日誌帶上真正送出的 opcode）；
  新增 `projectileItemOf`。
- 測試 **+2 → 403**（`0x24`／`0x25` 的 golden bytes 與轉播對照）；`whisper_probe.mjs` 多兩段（射擊、魔法）。
- 未實作：`afterimage` 的正確子節點、`speed` 的抖動來源（同 ADR-026），以及 `0x24` 特效內部那一組
  （`right[18] + 120*Value`／`sub_514BA0`）——轉播不需要它們。

## ADR-028：c2s 攻擊的第 2 欄是**技能 id**，不是「游標下的怪」—— `clickedMobId` 改名 `skillId`

**日期**：2026-10-17 ｜ **狀態**：已定案（更正 §4.13.1 的欄位命名；**不動任何位元組**）。

**決策**：`0x0F`／`0x10`／`0x11` 表頭第 2 欄那個 `u32` ＝**技能 id**（0 ＝ 這一擊沒有技能）。`ClientAttack.clickedMobId`
改名 `skillId`；describe 的 `clicked=` 改 `skill=`；`ATTACK_HEADER_BYTES` 的註解改成
「opcode + packed + skill id + action|facing + speed」。golden bytes 一個都沒動。

**證據**（三條，全部是 binary）：

1. `dword_5C2038` 是 **`CSkillInfo` 單例**：`sub_4BA4B0`（`.c:194709`）把 vtable 設成 `CSkillInfo::vftable`，
   成員是 `ZMap<long, ZRef<SKILLROOT>>` 與 `ZMap<long, ZRef<SKILLENTRY>>`。
2. **三個 sender 的 `right` 都從那裡來**：`.c:285381` 是 `sub_4BDD20((_DWORD *)dword_5C2038, v11, v7, &right)`，
   緊接著 `switch (*(this + 105))`（武器的動作家族）挑 sender——30–33／40–44 走 `sub_512F90`（`0x0F`）、
   45／46／47 走 `sub_513C80`（`0x10`）；`sub_512F90` 把 `*right` 寫進第 2 欄（`.c:279079`）。
3. **同一個 `right` 在 `sub_511630` 裡就是技能**：`*(right + 72)` 是它的等級陣列、`n30` 是等級索引
   （`*(*(right+72) + 120*n30 - 36)` 被夾到 ≥1），而 `sub_511630` 回傳的是 USE 分頁**格號**、item id 走 `Args`。

**理由**：被打的怪在**目標記錄**裡（每筆 `u32 mobId` ＋ `u8 動畫` ＋ 傷害），表頭不需要牠；把第 2 欄讀成
「游標下的物件」會讓 `0x0F` 與它的收端 `0x23` 對不起來（收端同一個位置是「技能等級 ＋〔技能 id〕」那一對），
也會讓伺服器以為那個值可以用來找怪。改名讓「這一擊是不是技能」有一個誠實的名字。

**被否決的選項與原因**：

- **保留 `clickedMobId`、只加註解**：名字會被下一個讀 code 的人當成事實（`targetCap` 就是這樣留下來的，見 ADR-026）。
- **拿這個值去場地裡查怪**：沒有證據；`applyDamage` 的目標一律來自目標記錄，這一點不變。

**後果**：

- `protocol/field.ts`（`ClientAttack.skillId`、`ATTACK_HEADER_BYTES` 註解、describe 的 `skill=`）、
  `protocol/schema.ts`（三個 opcode 的欄位名與註解）、`test/field.test.ts`（golden 值 0x30 保留：證明它會被原樣帶過）、
  `test/serve.test.ts`（那幾筆改成 0＝沒有技能）、`whisper_probe.mjs`（`skillId: 0`）。
- **伺服器行為零改變**：`loginserver.ts` 沒有任何 handler 讀過這個值。
- 順手把 §4.11.7 的 `0x28` 那一列讀完（`u32 flags` →〔bit 0／4／8 各一個 `u32`〕→ `u8`：非 0 就
  `sub_45F340` 讀 **id 清單**成 15 格、0 就用這個人自己的 look 區 → `sub_508260` → **`sub_508290`**，
  也就是 §4.11.7c 說的那條「觀察者怎麼知道那個人的武器」的路）。

## ADR-029：道具欄的拖放（c2s `0x17`）—— 伺服器只驗結構、兩格都有東西就是互換、丟到地上有落地規則、現金裝備不動

**日期**：2026-10-17 ｜ **狀態**：已定案（第一個「玩家自己搬東西」的 opcode；證據在 FINDINGS §4.36）。

**決策**：實作 c2s `0x17`（`[0x17][u8 tab][s16 fromSlot][s16 toSlot][s16 count]`，`sub_55ACB0`）
的四種動作——**穿戴**（tab 1、`to` 是負格）、**脫下**（`from` 是負格）、**分頁內搬移**、**兩格互換**
（線上完全一樣，互換只是「兩格都有東西」的結果）、**丟到地上**（`to = 0`，見追記）——而且**由伺服器決定結果**：成功回一個 `0x0B`
（`changes`：目的格 `put`、來源格 `clear`；互換是兩個 `put`），拒絕回**空的** `0x0B`，動到負格時
再送同圖其他人一個 `0x28`（不 echo 自己）。判定與寫入分成兩趟（先判後寫）放在純函式
`applyChangeSlot`（`game/inventory.ts`），呼叫者只負責送包與日誌。

**五個決策**（線路上沒有這些資訊，2003 的伺服器也不在了）：

1. **只驗結構，不驗需求**：`sub_4636B0` 在送出前用 `sub_4C5020`／`sub_4C5420` 算出角色總和再比
   `sub_465A30(itemId)` 的 `reqSTR/DEX/INT/LUK/level/fame`、職業位（`sub_4657F0`）與性別，但那是
   **客戶端自己的規則**，而且只替自己檢查。伺服器只拒絕「資料上不可能」的請求：不存在的分頁、
   超出格數、把消耗品放進穿戴格、把武器放進鞋子的部位。**不重讀 `reqLevel`／`reqJob`** —— 那是第二份
   沒有人能驗的 archive 規則，而且能力值在本專案仍是伺服器的權威（升級與能力點都還沒做）。
2. **兩格都有東西 ＝ 互換**（兩個方向都是）：把裝備拖到已佔用的部位 ＝ 舊的那件被放進新的一件來的格子，
   而互換只在被擠掉的那件放得回來源格時才接受（`displacedItemDoesNotFit`）。
3. **`count` 只有 `-1` 合法**（地面以外的四種動作）：三個搬移送出者都送字面上的 `-1`（整格），
   拒絕值是 `badCount`。丟到地上那條路的正數是客戶端問出來的（見追記）。
4. **丟到地上先不做**（`dropNotImplemented`）：`sub_463BE0` 送的是 `tab, from, 0, 數量`，但落地的規則
   （誰的東西、躺多久、誰能撿）屬於場地，`game/drops.ts` 目前只有怪物掉的那些與「走過去撿」。
   拒絕是安全的，**因為客戶端從來沒有自己搬過東西**：被拒的道具留在原地，客戶端的視窗只跟著 `0x0B` 動。
   ⇒ **2026-10-17 由追記取代**（落地規則做完了；`dropNotImplemented` 已從拒絕值移除）。
5. **現金裝備不動**：`sub_463490` 的游標 switch 允許指到穿戴格 `12`／`13`（現金裝備），但客戶端自己把 id
   歸進 15 格的那張表（`sub_45F340`）對 `111xxxx` **直接丟掉**（沒有那一格），所以本伺服器一律拒絕（`wrongPart`）。
   寧可少穿一件，也不要送一個會讓客戶端丟 `AVCDisconnectException` 的 `0x0B`（§4.6 的收尾檢查）。

**理由**：

| 考量 | 說明 |
|---|---|
| 閘門 | 四個送出者都**不動客戶端的道具欄**，送完就把 `CWvsApp + 0x18` 設成 1；能清掉那一格的只有 `0x0B`（`result != 0`，§4.6）。所以拒絕**必須回包**，否則玩家第一次被拒之後整個道具欄就再也不能互動（與 §4.34.2 同一條規則） |
| 誰是權威 | 伺服器持有紀錄（ADR-017），`0x0B` 是唯一能改客戶端道具欄的封包；「伺服器算、客戶端跟著」比「客戶端自己改、再想辦法同步」少一整套回滾邏輯 |
| 證據邊界 | 負格 ＝ 已穿戴、`toSlot = 0` ＝ 地上、`count = -1` ＝ 整格，三件都是 binary 裡讀出來的；部位檢查用 `sub_45F340` 的表（客戶端自己用的那一張），不新增規則 |

**被否決的選項與原因**：

- **照抄客戶端的需求檢查（`reqSTR`…）**：要維護第二份 archive 規則，而且沒有任何流量能驗它；
  能力值改動一來（升級／能力點）它就開始漂移。
- **沉默＝拒絕**：會鎖死整個道具欄（見上面的閘門）。
- **自己做落地**（原第 4 點的理由）：需要 field 的歸屬／壽命／可撿範圍三個選擇，而 client 這一半
  （`0x43`／`0x44`）已經有了。**已由追記推翻**：使用者要「丟到地上」，而落地用的三個常數全部沿用既有的
  （`DROP_LIFETIME_MS`、可撿範圍、「比最後一次移動更早」），沒有猜新的。
- **兩格都有東西時先搬到暫存格**：客戶端的 `0x0B` 有 `op 2`（swap）可用，但「兩格都有東西」在
  線上就是一次互換，用兩個 `put` 表達與 client 的語意一致，也不必解釋暫存格的去向。

**後果**：

- `protocol/field.ts`（`CLIENT_FIELD_OPCODE.changeSlot`、`readClientChangeSlot`／`encodeClientChangeSlot`／
  `describeClientChangeSlot`、`FIELD_OPCODE.userLook`、`UserLook` 與三個 codec）、
  `protocol/schema.ts`（`0x17` byte-exact、`0x28` partial 兩列）、`game/inventory.ts`、
  `test/field.test.ts`、`test/inventory.test.ts`、`test/serve.test.ts`（同場兩人：穿戴者收 `0x0B`、
  觀察者收 `0x28`、穿戴者沒有自己的 `0x28`）、`whisper_probe.mjs`（脫下武器再穿回去）。
- **`0x28` 的第一個送出者**：在此之前 s2c `0x28` 只有 codec 沒有呼叫者；現在換裝備會走它，
  session 的 `avatarItems` 也必須在換裝時更新（否則下一個進場的人會看到舊的 look）。
- **不重算裝備加成**：客戶端自己算傷害（§4.17），所以換武器不動伺服器帳上的任何數字；
  「換武器 → 攻擊動作家族改變」也在客戶端（§4.11.7c）。
- 存檔自動跟上：`items` 就是紀錄的一部分（ADR-017），不需要新的存檔欄位。
- **丟到地上的後果**（追記）：`game/inventory.ts` 多一個 `{kind: "drop"}` 與 `cashItem` 拒絕值；
  `game/drops.ts` 多 `DropEntry.kind`／`slot` 與 `dropFromPlayer`；`game/world.ts` 多
  `FieldInstance.dropItem` 與 `FieldMember.lastMoveAt`；`game/rewards.ts` 的 `grantItem` 多一個
  `template`（`freshSlot`），撿回來的裝備是同一件。

## ADR-029 追記：`toSlot = 0` 真的落地 —— 第 4 點由「先不做」改成「有落地規則」

**日期**：2026-10-17 ｜ **狀態**：已定案（**取代原第 4 點**：`dropNotImplemented` 從 `ChangeSlotFailure`
移除，改成 `{kind: "drop"}` 與新的拒絕值 `cashItem`；原第 1、2、3、5 點不變）。

**決策**：`0x17` 的第四種動作（`tab, from, 0, 數量`，`sub_463BE0`）現在會真的把東西放到地上：

| 問題 | 答案 | 依據 |
|---|---|---|
| 東西歸誰 | 場地（`FieldInstance.dropItem`），和怪物掉的走同一個 `DropField` | `0x43` 的欄位一個都沒多 |
| 用哪個 `0x43` | `DROP_KIND.placed`（`kind 2`）：**沒有怪物區塊**，線路 15 B | `placed` 是唯一不需要 `mobId` 的形狀（§4.18.2） |
| 掉在哪 | 玩家站的地方，**不擴散、不查腳踏點** | 客戶端沒動過自己的道具欄，東西必須落在它畫著玩家的地方 |
| 數量 | 客戶端問出來的數（`tab == 1` 固定 1、`itemId/10000 == 207` 整疊），伺服器只跟堆疊數比對 | §4.36.1；「丟幾個」是客戶端已經決定的事 |
| 誰撿得到 | 同圖、走到範圍內（40 / 上下 60 px）、**且這筆掉落比你的最後一次移動更早** | 見下；沒有請求也沒有按鍵（§4.18.6 第 4 點） |
| 躺多久 | `DROP_LIFETIME_MS`（300 s）後 `0x44 kind 0` | 與怪物掉的一樣，不新增常數 |
| 撿回來的是什麼 | **同一件**：`slot` 留在落地紀錄裡，`ruc`／`cuc`／捲軸加成都在 | 地上的東西是那件東西，不是它的 id 的複本 |
| 現金道具 | 一律拒絕（`cashItem`） | 序號只存在道具欄那一格，落地紀錄沒有地方放它 |

**「必須在這筆掉落之後動過」**（`DropField.reachable(x, y, movedAt)`、`FieldMember.lastMoveAt`）：這一條同時解
兩個問題，兩邊各自都足以要求它——怪物掉落的**落點就在殺牠的人腳下**（擴散 ≤ 24 px），沒有這條規則它會在下一
個 tick 被同一個人立刻吸走，客戶端根本看不到「從屍體飛出來」；而玩家丟的東西**一定在自己腳下**，沒有這條
規則就會被自己馬上撿回來（等於丟不掉）。進入場地本身算一次移動。這是伺服器自己的選擇（ADR-007）：binary
這一半在 client。

**被否決的選項與原因**：

- **維持「先不做」**：使用者要「丟到地上」；而且原 client 有送出者（`sub_463BE0`）、有「몇 개나 버리시겠습니까?」
  對話框，不做就等於玩家永遠丟不掉東西。
- **只擋掉「丟的人自己」**：怪物掉落就沒有動畫時間了（屍體腳下立刻消失），而且需要兩套規則。
- **冷卻時間**（落地後 N 秒才能撿）：多一個常數與計時器，能表達的東西與「動過」一樣，而 `lastMoveAt`
  是已經存在的資料（`0x0E` 的處理本來就在更新位置）。
- **落地不送 `0x0B`**（只送 `0x43`）：客戶端從來沒有自己搬過東西（§4.36.2），不送的話那一格永遠不會空。
- **落地紀錄只留 itemId**：捲軸加過的裝備會變成全新的（資料遺失），而留住物件只多一個欄位。

**驗證**：`test/inventory.test.ts`（丟一部分／整疊／裝備只能 1／`cashItem`／`badCount`）、`test/drop.test.ts`
（`dropFromPlayer` 的落點、15 bytes、模板欄位、「必須先動過」）、`test/serve.test.ts`（真 socket：`0x0B`＋
`0x43` 給全場→站著不動與走開 80 px 都不撿→走回去才 `0x44`＋`0x0B`＋`0x11`；`count = 0` 是空的 `0x0B`）、
`whisper_probe.mjs`（把武器丟到地上再走過去撿回來）。

## ADR-030：組隊（s2c `0x10`／c2s `0x26`）—— 隊伍住在世界層、隊長退隊＝解散、下線＝退隊、每個請求都有回答

**日期**：2026-10-17 ｜ **狀態**：已定案（證據在 FINDINGS §4.37）。

**決策**：實作 2003 年的組隊，也就是 c2s `0x26` 的五個 type（`0` 建立／`1` 退出／`2` 接受邀請／`3` 邀請／
`4` 踢人，送出者是四個聊天指令與邀請對話框的「是」）與 s2c `0x10` 的回包。隊伍是**世界層**的狀態
（`GameEntryServer.parties`，`game/parties.ts` 的 `PartyRegistry`），名冊是 **6 × (u32 角色 id ＋ 13-byte
名字)** ＝ 102 bytes（FINDINGS §4.37.4），請求的處理在 `net/loginserver.ts` 的 `handlePartyRequest`。

送出的 `0x10` 只用到八個 type（下面九列——`10` 有兩種形狀；`sub_55C5E0` 有 case 的也只有
`3`／`5`／`6`／`7`／`8`／`10`／`11`／`13`／`14`／`15`，其餘一律丟掉）：

| 什麼事 | 送什麼 | 給誰 |
|---|---|---|
| 建立成功 | `6`（partyId）| 建立的人（client 自己把自己寫進名冊第 0 格）|
| 邀請 | `3`（inviterId ＋ 邀請者的名字）| 被邀請的人（模態對話框）|
| 接受邀請 | `13`（partyId ＋ 加入者的名字 ＋ 新名冊）| **全體**（含加入者；名字是自己時 client 印「파티에 가입되었습니다.」）|
| 退出／被踢 | `10` `flag 1` ＋ `kicked` ＋ 名字 ＋ 新名冊 | **全體**（含離開的人；自己的 id 在封包裡是它清掉 party id 的唯一方法）|
| 隊長退出 | `10` `flag 0` ＋ partyId ＋ 隊長 id | **全體**（含隊長；沒有名冊、沒有名字）|
| 已經在隊伍裡（create／invite 的對象）| `7` | 請求的人 |
| 不在隊伍裡（leave／accept／invite／kick 的前置）| `11` | 請求的人 |
| 隊伍已滿 | `15` | 接受邀請的人 |
| 其他（邀請失效、不是隊長、目標不在線上…）| `0`（client 的 default）| 請求的人 |

**五個決策**（線路上沒有這些資訊，2003 的伺服器也不在了）：

1. **隊伍住在世界層，不在場地層**：名冊裡沒有地圖（§4.37.4），隊員分散在兩張圖是合法的；`0x1C`／`0x1D`
   的場地廣播辦不到跨圖，所以送包走 `sessionsByCharacter`（跟密語／找人同一條路）。
2. **隊長退隊 ＝ 解散**：`0x10 type 10 flag 0` 的兩句訊息就是這件事（「파티장을 그만둡니다. 파티가
   해체되었습니다」／「파티장이 파티를 그만둬서 파티에서 나갑니다」），而封包裡**沒有任何「換隊長」的欄位**。
3. **下線 ＝ 退隊**（隊長下線 ＝ 解散）：2003 的隊伍是記憶體狀態，名冊只有 6 格、沒有「離線」這個狀態；
   這也與「一個角色只有一條連線」（ADR-018）一致。
4. **邀請一目標一格**，後到的蓋掉前一個；接受時再驗一次「邀請者的隊伍還在、還有位子」。`0x26 type 2` 帶的
   是 **inviterId** 而不是 party id，所以伺服器**必須**記住誰邀請了誰。
5. **每一個請求都回一個 `0x10`**，包含拒絕：`0x26 type 2` 是模態對話框的答案（client 在等），而其他 type
   的訊息（「이미 가입한 파티가 있습니다」…）也只能由伺服器送——client 沒有本地的失敗路徑。

**理由**：

| 考量 | 說明 |
|---|---|
| 誰是權威 | 隊伍只存在伺服器上；client 的 `CWvsApp + 404`（party id）與 102-byte 名冊是**被寫的那一邊**，它沒有任何送出者會改自己（FINDINGS §4.37.3） |
| 證據邊界 | 五個請求、九個回包、名冊的形狀、兩種 `flag` 的意思全部是 binary 讀出來的；「誰能邀請誰」「隊伍幾個人」也是 client 自己的常數（6 格），沒有新增規則 |
| 失效處理 | 邀請不是狀態機：接受時重新驗「隊伍還在＋有位子＋自己不在隊伍」，所以不需要過期時間，也不需要清理常式 |
| 跨圖 | 名冊沒有地圖，強迫同圖只會多一條沒有證據的規則；client 的 `/파티초대` 查不到別圖的人是**client 的限制**，不是協定的限制（§4.37.7） |

**被否決的選項與原因**：

- **隊伍放在 `FieldInstance`**：最後一個人離開場地時場地仍然活著（ADR-012），但隊伍會跟著「這張圖」走——
  兩個人各自過圖之後就看不見彼此了，而名冊裡根本沒有地圖可以重建。
- **隊長退隊時把隊長傳給下一個人**：`0x10` 沒有這個欄位。硬送 `type 6` 會讓 client **清空名冊**再把自己寫進
  第 0 格（還印「새로운 파티를 만들었습니다」），送 `type 13` 只會換名冊、不會換 `+404` 的 party id 與
  leader 判斷（client 用 `*(CWvsApp+102) == *(CWvsApp+5)` 判斷自己是不是隊長）——兩條都是錯的訊息。
- **隊伍寫進存檔（離線保留）**：存檔的 schema 是帳號 → 角色（ADR-017），加一張隊伍表等於發明一個 2003 沒有
  的狀態，而且 client 的 `/파티정보` 也不會因為重新登入而自己恢復。
- **用 `type 5` 當「建立成功」的回包**：它是安靜的整份同步（沒有訊息、client 不會把自己補進名冊），
  `type 6` 才是 client 為建立準備的那一個。
- **邀請只存在 client**：`type 2` 只帶 inviterId，沒有 party id，伺服器不記就無法回答「哪一隊」。
- **沉默拒絕**：`type 2` 是模態對話框，其他 type 的錯誤訊息也只能由伺服器送（見決策 5）。
- **跨圖邀請一律拒絕**：沒有任何證據要求它，而且隊伍本來就是世界層的（決策 1）。

**後果**：

- 新檔：`protocol/party.ts`（`0x10`／`0x26` 的 codec、102-byte 名冊、`describe*`）、`game/parties.ts`
  （`PartyRegistry`：建立／加入／邀請／退出，隊長離開＝解散）。
- `net/loginserver.ts`：`handlePartyRequest`／`broadcastPartyLeave`／`leaveParty`；連線結束時**先**從
  `sessionsByCharacter` 移除**再**退隊（不要對已經關掉的 socket 送包）。
- `protocol/field.ts`：`describeClientFieldPacket` 認得 `0x26`、`describeFieldPacket` 認得 `0x10`。
- `protocol/schema.ts`：`0x10` 新增一列 byte-exact；`0x26` 由 `partial` 升為 byte-exact。
- 測試：`test/party.test.ts`（10 則：golden bytes、round-trip、名冊、registry）、`test/serve.test.ts`
  （同場兩人走完 create → invite → accept → leave → 隊長 leave → 沒有隊伍的 leave）、
  `whisper_probe.mjs`（真 CLI，+10 個檢查）。
- **沒有存檔變更**：隊伍不進 `--save`（見被否決的選項），角色紀錄一個欄位都沒動。
- 跨圖送包的路多了一個使用者：`sessionsByCharacter` 原本只有密語／找人在用。

## ADR-031：人氣（c2s `0x20` → s2c `0x12`）—— 15 級才能給、一天一次、同一個對象一個月一次、配額只活在記憶體

**日期**：2026-10-17 ｜ **狀態**：已定案（證據在 FINDINGS §4.38）。

**決策**：實作角色右鍵選單的「인기도 +／-」（`0x20` ＝ `u32 目標角色 id` ＋ `u8 up`，送出者是
`sub_55D7B0`）與它的六種回包（`0x12`：`0` 成功（給送出者）、`1` 什麼都不顯示、`2` 初學者、
`3` 今天已經給過、`4` 這個月給過同一個人、`5` 通知被給的人）。規則在純函式 `applyFame`
（`game/fame.ts`），配額在世界層的 `FameLedgers`，送包在 `net/loginserver.ts` 的 `handleFameRequest`。

**五個決策**（線路上沒有這些資訊，2003 的伺服器也不在了）：

1. **初學者的界線 ＝ 15 級**（`FAME_MIN_LEVEL`）：client 只有 5 分鐘的本地冷卻，沒有任何等級檢查，
   所以「초보자는 인기도를 올리거나 내리지 못합니다」一定是伺服器說的；15 是 2003 年的常識值。
2. **「今天」與「這個月」用 UTC 的日序號與月序號**：不隨時區或重開機跳動，也讓「월」那一句有明確界線。
3. **順序是「自己 → 初學者 → 這個月 → 今天」**：同一個人、同一天再給一次時 client 顯示的是
   「이번 달에는…」（type 4）而不是「오늘은…」（type 3），所以月比日先問。
4. **人氣夾在 `[0, 65535]`**：紀錄是 u16，往下給 0 分的人不會變成負數。
5. **目標用場地找**（`FieldInstance.member`）：client 的選單只看得見同一張圖的人（`CUserPool`），
   查不到就是過期的 id → 回 `type 1`（什麼都不顯示），不編一個訊息。

**理由**：

| 考量 | 說明 |
|---|---|
| 誰是權威 | 人氣是角色紀錄的一欄（`CharacterData.fame`），由伺服器加減；client 只負責顯示 `0x12` 與 `0x0D` |
| 為什麼要 `0x0D` | 被給的人的能力視窗要跟著動，而唯一能改它的封包是 `0x0D`（`fame` 的 bit `0x20000`）；給的人自己沒變，所以**不送** |
| 為什麼不重做冷卻 | 5 分鐘是 client 的規則（`*(app + 0x2AC)`），重做只會多一個常數；偽造的封包就算繞過它，也還是會被日／月配額擋住 |
| 為什麼不進存檔 | 它不是角色狀態（`CharacterData` 沒有那一格、`0x0D` 也沒有它）；要留住得替 `AccountRecord` 加新欄位，那是新的存檔語意 |
| 為什麼 `type 1` 用在「不在這張圖」 | client 有一個「什麼都不顯示」的 case，而「找不到人」在 client 端已經是本地訊息（`sub_55D7B0` 不會送包）；伺服器這一側對過期的 id 保持安靜最安全 |

**被否決的選項與原因**：

- **把配額寫進存檔**：`AccountRecord` 目前是「帳號 → 角色」，配額是「角色 → 日／月／名單」的第三張表；
  而且 2003 的伺服器怎麼記完全看不出來。留成 OPEN（§4.38.2），要做的話欄位形狀已經寫在文件裡。
- **被給的人也要 ≥ 15 級**：沒有任何證據；多的規則會讓「為什麼他不能給我人氣」變成第二個猜測。
- **用本地時間算日／月**：時區一換（或主機設錯）配額就跳動；UTC 是唯一不會有歧義的選擇。
- **允許跨圖給人氣**：client 送不出這種封包（選單來自 `CUserPool`），而遠處的人氣也沒有任何回饋畫面。
- **給的人也送 `0x0D`**：他的人氣沒變，送了只會讓 client 重畫一次（`diffStats` 也會是空的）。
- **所有失敗都回 `type 1`**：`2`／`3`／`4` 是 client 準備好的三句訊息，不回它們就等於把 client 的文案丟掉。
- **用 `type 5` 當成功回給送出者**：`type 5` 的第二個名字是**自己**（client 自己補），送給送出者會變成
  「'X'님께서 '自己'님의…」——那是對被給的人說的句子。

**後果**：

- 新檔：`protocol/fame.ts`（`0x20`／`0x12` 的 codec 與 `describe*`）、`game/fame.ts`
  （`applyFame`／`fameClock`／`FameLedgers`）。
- `net/loginserver.ts`：`handleFameRequest` 接在 `0x26` 的隊伍請求旁邊（兩個都是「一個請求一個答案」）；
  成功時**三個**收件者（給的人 `type 0`、被給的人 `type 5` 與 `0x0D`）。
- `protocol/field.ts`：`describeClientFieldPacket` 認得 `0x20`、`describeFieldPacket` 認得 `0x12`。
- `protocol/schema.ts`：新增 c2s `0x20` 與 s2c `0x12` 兩列（70 個封包：46／20／4）。
- 測試：`fame.test.ts` 10 則、`serve.test.ts` 一條兩 socket 的（442 個測試）、`whisper_probe.mjs`
  兩項（真 CLI：1 級的角色拿到 `type 2`，目標什麼都沒收到）。
- **沒有存檔變更**：人氣加減寫在角色紀錄裡（跟經驗值一樣），配額不進存檔（§4.38.2）。

## ADR-032：交易（c2s `0x25`／s2c `0x50`）—— 東西留在自己身上到成交、兩邊都確認才原子交換

**日期**：2026-10-17 ｜ **狀態**：已定案（證據在 FINDINGS §4.39／§4.40）。

**決策**：實作 1:1 교환 的完整流程。`0x25` 是**開著的視窗共用的請求**（七個 type），`0x50` 是它的
回包（`sub_4815E0`，交易會用到其中十一種）。codec 在 `protocol/miniroom.ts`，規則在 `game/trades.ts`，
送包在 `net/loginserver.ts` 的 `handleMiniRoomRequest` 與七個 `trade*`／`leaveTrade`。

**七個決策**（線路上有這些欄位，但「什麼時候送哪一個」是這份 repo 的規則）：

1. **`0x25` 的七個 type 全部認得，未知的只記一行**：client 不會送表外的值，送了就是壞掉的封包；
   伺服器不解釋、也不回包——回一個 client 不認得的 type 只會讓它斷線。
2. **道具留在自己的庫存裡，直到成交**：`sub_4D5C80` 只送「哪一格、幾個、放到第幾格」，沒有
   `0x0B`；所以伺服器也不動它。這讓「取消」不需要任何還原動作，代價是成交時要**重新驗證**。
3. **成交是原子交換**：`settleTrade` 先 `structuredClone` 兩邊的庫存，在副本上扣／加，任何一步
   失敗（東西不在了、對面放不下、錢不夠）就整個丟掉，回 `{ok:false}`，真正的 `CharacterItems`
   一格都不動。
4. **兩邊都按下確認才交換**：一個 `0x25 type 13` 只把 `TradeSide.confirmed` 設起來；兩邊都 true
   時才送 `0x50 type 13`（鎖定）→ 交換 → `type 8 code 3`。
5. **成交後用既有的 `0x0B`＋`0x0D` 更新兩邊**：庫存只有 `0x0B` 能改、錢只有 `0x0D` 能改
   （§4.36／§4.21），所以交易結果不是新封包，就是這兩包。`type 8` 只負責關窗與顯示那一句話。
6. **邀請 30 秒逾時**（`TRADE_INVITE_TTL_MS`）：client 的模態只有「是」會送包（`sub_481910`），
   沒有「拒絕」，所以沒有逾時就會永遠停在「等待對方回答」。
7. **交易格是 1..8、裝備的 `count` 一定是 1**：`sub_4D63C0` 的 `y` 對 `<= 0` 直接放棄，
   `sub_4D5C80` 對 `tab == 1` 根本不寫 `count`。

**理由**：

| 考量 | 說明 |
|---|---|
| 為什麼房間住世界層 | 房間橫跨兩個 session（`TradeRegistry` 在 `loginserver` 的 world 那一側），關掉一個連線不能讓另一個人的視窗失去對手 |
| 為什麼不托管道具 | 托管要多兩個封包（「拿走」與「還原」），而且 `0x0B` 的格子語意會被交易污染；2003 的 client 根本沒有「交易中的道具不在庫存」這個狀態 |
| 為什麼要重新驗證 | 交易窗口可以開幾分鐘；這期間玩家可以丟掉、賣掉或使用那件東西。驗證放在**交換前一刻**，錯誤就不能被隱藏 |
| 為什麼成功要送 `0x0B` | 兩邊的庫存都變了（一邊少、一邊多），而 client 的庫存只認 `0x0B`；不送就是畫面與紀錄不一致 |
| 為什麼 `0x0D` 只給有變的人 | 錢沒動的一邊送 `0x0D` 只會讓它重畫一次（`diffStats` 也會是空的） |
| 為什麼 `type 8` 不自己發明 code | 三句訊息（성사／취소／실패）在 client 自己的字串表裡，`sub_4D3D70` 只認 1／3／4 |

**被否決的選項與原因**：

- **交易開始時先從庫存扣掉（托管）**：見上；而且「取消」會需要一個 client 沒有處理的還原封包。
- **用新 opcode 送交易結果**：沒有證據；`0x50 type 8` 就是為此存在的。
- **讓確認只由一邊決定（按下即成交）**：`type 13` 的 s2c 是「鎖定」，client 的 UI 也把它畫成
  鎖頭；一邊按了就換等於跳過對方最後一次確認。
- **不驗證、直接相信 client 的 offer**：交易窗口可以開幾分鐘，這是唯一會讓玩家憑空生出道具的路。
- **`tab == 1` 也讀 `count`**：client 不寫那個欄位，讀了會把後面的 `roomSlot` 當成 count。
- **把「另一個視窗開著」的閘門搬到伺服器**：那是 client 的 UI 限制（`this_15`）；伺服器同時開商店
  與交易不會產生任何 client 會斷線的封包，複製它只會多一條規則要維護。

**後果**：

- 新檔：`protocol/miniroom.ts`（`0x25`／`0x50` 的 codec、`describe*`、`MINIROOM_*` 常數）、
  `game/trades.ts`（`TradeRegistry`／`settleTrade`／`isTradeSlot`）。
- `net/loginserver.ts`：`handleMiniRoomRequest` 接在 `0x20` 旁邊；斷線時 `leaveTrade(…, "disconnected")`
  讓對方收到 `type 8 code 1`。
- `protocol/field.ts`：`describeClientFieldPacket` 認得 `0x25`、`describeFieldPacket` 認得 `0x50`。
- `protocol/schema.ts`：c2s `0x25` 從 skeleton 就地升級成 byte-exact ＋ 新增 s2c `0x50`
  （**71 個封包：48／20／3**）。
- 測試：`miniroom.test.ts` 13 則、`serve.test.ts` 兩條兩 socket 的（**457 個測試**）、
  `whisper_probe.mjs` 八項（真 CLI：邀請、答應、兩邊進房、放錢、兩邊確認、鎖定、`0x0D`、成交）。
- **沒有存檔變更**：交易只改 `CharacterData.items` 與 `mesos`，兩者本來就在存檔裡。
- 🟡 三個欄位仍是推論，文件已標：participant 的第一個 byte（送等級）、`type 5` 的第一個 byte（送 0）、
  `type 4` 的結束 byte（送 `0xff`）。
